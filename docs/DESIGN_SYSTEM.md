# Design System

Direction: **calm, adult-oriented Material 3**, evolved toward more visual energy from 2026-09-09 onward (see the vivid-accent and "full energy" entries in Last verified above) — restrained surfaces and generous spacing stay, but key accents (the brand `primary` colour, Home's hero card, daily-task tiles) are now deliberately vivid and saturated rather than muted, based on real-device feedback that the earlier, flatter palette read as bland next to mainstream apps. Still: one modest gamification element (a streak/progress indicator, not XP/badges/leaderboards), never a stats-heavy or celebratory-on-every-success feel. Must work equally well in Arabic (RTL) and English (LTR).

## Color

Generated via `ColorScheme.fromSeed(seedColor: ..., brightness: ...)` — Material 3's tonal-palette algorithm derives the full light/dark role set (`primary`, `onPrimary`, `primaryContainer`, `secondary`, `tertiary`, `surface`, `surfaceVariant`, `error`, etc.) from one seed colour per theme, which is what makes "selectable colour themes" (Settings, per the app's requirements) a matter of swapping a seed value rather than hand-maintaining N full palettes.

**Default seed — `color.seed.calm-teal`: `#2A6F77`.** Chosen to read as calm/trustworthy rather than energetic (unlike the old bright `#3FB950` green), while keeping a plausible growth/learning association. Representative derived roles (exact values are the algorithm's output, not hand-picked — regenerate via Flutter's Material theme builder or `ColorScheme.fromSeed` at implementation time):

| Role | Light (approx.) | Dark (approx.) | Usage |
|---|---|---|---|
| `colorScheme.surface` | near-white, warm neutral | near-black, warm neutral | App/screen background |
| `colorScheme.surfaceContainer` | light neutral | dark neutral | Cards, exercise panels |
| `colorScheme.onSurface` | near-black | near-white | Primary text |
| `colorScheme.onSurfaceVariant` | mid grey | light grey | Secondary/help text |
| `colorScheme.primary` | **hand-picked flat brand accent** — see below | lighter teal tone (pure algorithm output) | Primary actions, selected/focused state |
| `colorScheme.error` | muted red | lighter muted red | Errors, "incorrect" feedback |
| `colorScheme.tertiary` | muted warm tone | lighter warm tone | Hints, informational callouts |

**Light-mode `primary`/`primaryContainer` are overridden, every other role is not (`AppColorSeed.brandPrimary`/`onBrandPrimary`/`brandPrimaryContainer`/`onBrandPrimaryContainer`, applied in `AppTheme._build`).** `ColorScheme.fromSeed`'s own light-mode `primary` sits at a deliberately dark tone (to guarantee white-text contrast), which read closer to ink than to an accent and prompted a "the app feels muted next to WhatsApp/Telegram" report. Since `primary` is the one role behind buttons, selected answers, progress fills and the "correct" state (see Components below), swapping just that role for a flat, saturated tone in the same hue family fixes the complaint without touching the calm surfaces/secondary/tertiary/error roles the original ADR 0004 direction still holds for.

The first pass overrode only `primary`/`onPrimary` and left `primaryContainer` as the algorithm's own pale, near-pastel tint — which produced a follow-up report ("some are vivid and some are mute"): the "Correct!" feedback banner (since moved to `feedbackTheme.successContainer` — see Semantic feedback tokens above) and Home's "Continue learning" card both used `primaryContainer`, sitting right next to the now-vivid `primary` buttons/chips, so the pale container read as a mismatched, muted surface rather than a lighter tint of the same accent. `primaryContainer`/`onPrimaryContainer` are now overridden too, with a punchier (still clearly lighter than `primary`, just not desaturated all the way to pastel) tint in the same hue family. The Settings colour-theme picker previews `brandPrimary` (not the raw `seedColor`) for the same reason — an earlier version showed the muted seed while the rest of the app showed the vivid accent, two visibly different colours for the same "theme."

Each value (`brandPrimary` and `brandPrimaryContainer`) was swept across lightness at full saturation and checked against the 4.5:1 WCAG 2.1 AA floor with its paired on-colour — white passes for `slate-indigo`/`warm-terracotta` but not for `calm-teal` (a vivid cyan), mirroring `GamificationTheme.onStreakAccent`'s own white-fails-AA case below. Dark mode is left as pure algorithm output: its `primary`/`primaryContainer` are already light, visible tones against the dark surface, so they don't have the same problem.

`colorScheme.tertiary` (used by `StatusIndicator`'s `inProgress`/`needsReview` states — the half-filled/refresh icons on every lesson, unit, and vocabulary row) is a known remaining gap: it's still the algorithm's muted tone, so it can still look flat next to a `mastered` row's now-vivid `primary` checkmark on the same list. Left alone deliberately for now, pending a decision on what an accessible "in progress" accent should be (not simply `primary` again — the two states need to stay visually distinct).

| Seed | `brandPrimary` (light `primary`) | `onBrandPrimary` | `brandPrimaryContainer` (light `primaryContainer`) | `onBrandPrimaryContainer` |
|---|---|---|---|---|
| `color.seed.calm-teal` | `#00CBE5` | `#00363C` | `#3DE8FF` | `#00363C` |
| `color.seed.slate-indigo` | `#3645E2` | `#FFFFFF` | `#9DA4F1` | `#1F2C61` |
| `color.seed.warm-terracotta` | `#C74605` | `#FFFFFF` | `#FBA174` | `#542105` |

**Approved alternate seeds (no longer user-selectable since 1.0.0; the app uses `kAppColorSeed` = calm teal):** `color.seed.slate-indigo` (`#3F4A7A`), `color.seed.warm-terracotta` (`#8A5238`) — same generation mechanism, swap the seed. No theme may be added ad hoc outside this approved list without updating this doc.

**Semantic feedback tokens (`FeedbackTheme`, a `ThemeExtension`, not `ColorScheme` roles):** `success`/`onSuccess`/`successContainer`/`onSuccessContainer` — a fixed, real green used for every "this answer is correct" visual, deliberately independent of the active colour-theme seed. Once `primary` (above) became a per-theme brand accent rather than a fixed hue, a correct answer under `warmTerracotta` would otherwise fill orange, which doesn't read as affirming the way green universally does. Used by: `ChoiceActivityView`'s correct option (fill = `success`, text/icon = `onSuccess`; border variant on media options), `ActivityFeedbackBanner`'s correct case (`successContainer`/`onSuccessContainer`, mirroring how `primaryContainer` is used for its other states), and `StatusIndicator.mastered` (`success`). The `neutral`/"selected but not yet graded" states in these same components are unaffected and still use `colorScheme.primary` — that represents the learner's pick, not a verdict. Values: `success` `#157A36` light / `#4ADE80` dark, `onSuccess` `#FFFFFF` light / `#0B2E17` dark, `successContainer` `#E3F5E8` light / `#16311F` dark, `onSuccessContainer` `#0F5C28` light / `#7EE39C` dark — each pair checked against the 4.5:1 WCAG 2.1 AA floor.

**Gamification tokens (`ThemeExtension`, not `ColorScheme` roles):** `streakAccent` — a single warm amber (`#B7791F` light / `#D9A441` dark), used *only* for the one streak/progress element on Home per the "light gamification" decision. Deliberately not reused elsewhere, so it doesn't creep into a general accent colour the way the old `color.accent` did. Its paired foreground is `onStreakAccent` (`#1A1200` light / `#2B1D00` dark) — **always use it for content drawn on `streakAccent`, never `colorScheme.onPrimary`**: `onPrimary` is white in the light theme and computes to only 3.64:1 on `#B7791F`, below the 4.5:1 AA floor in [UX_PRINCIPLES.md](UX_PRINCIPLES.md). The shipped pairs measure 5.10:1 (light) and 7.30:1 (dark).

Exercise feedback (correct/incorrect) is never colour-alone — always paired with an icon + text, per [UX_PRINCIPLES.md](UX_PRINCIPLES.md).

### Semantic neutral tokens (`AppTokens`, `lib/core/theme/app_tokens.dart`)

The page, card, text and border colours every screen is built from. **Neutral, not seed-tinted** — picking a colour theme in Settings changes the accent only, never the greys (earlier builds derived surfaces from the seed, which is why the whole app read teal-grey). `AppTheme` sets `ColorScheme.surface`/`onSurface`/`onSurfaceVariant`/`outlineVariant` and the `surfaceContainer*` ramp from these same values, so stock Material widgets on every screen inherit them.

| Token | Light | Dark | Usage |
|---|---|---|---|
| `page` | `#F5F3F0` | `#121110` | Screen background (`scaffoldBackgroundColor`, `colorScheme.surface`) |
| `card` | `#FFFFFF` | `#1D1B19` | Raised containers — always *lighter* than `page`, in dark too (a darker card reads as sunken) |
| `cardMuted` | `#EFECE8` | `#282522` | Pills, progress tracks, quiet states |
| `border` | `#E7E2DC` | `#34302C` | Hairlines only (nav top edge, dark-mode hero). Separation comes mostly from `card` vs `page`, not outlines |
| `textPrimary` | `#1C1917` | `#F3EFEA` | Headings, body |
| `textSecondary` | `#635C55` | `#ABA49C` | Meta/supporting text — ≥4.5:1 on `page`, `card` and `cardMuted` |
| `primaryInk` | `AppColorSeed.brandInk` | generated dark `primary` | The accent as *text, icon or progress fill on a neutral surface*, and the filled-button fill |
| `onPrimaryInk` | `#FFFFFF` | generated dark `onPrimary` | Text and icons on a solid `primaryInk` fill — filled buttons, the lesson player's play/mic buttons (≥4.5:1, tested) |
| `primaryInkTint` | `primaryInk` 12% over `card` | `primaryInk` 20% over `card` | The selected-state fill: a chosen answer, a paired tile, the nav indicator. `textPrimary` ≥4.5:1 on it, `primaryInk` ≥3:1 (tested) |

**`primaryInk` vs `colorScheme.primary`:** `primary` stays the seed's vivid brand fill (still used by option/selection states). `primaryInk` exists because `calmTeal`'s cyan `#00CBE5` is only ~1.9:1 on white — illegible as text or a progress fill, and it can only carry *dark* button text, which reads as a toy. `calmTeal`'s ink is `#007A87` (5.1:1 on white, white text 5.1:1); for `slateIndigo`/`warmTerracotta` the brand fill already passes 4.5:1, so their ink equals `brandPrimary`. Filled buttons use `primaryInk` + `onPrimaryInk`; text buttons, outlined buttons, the text cursor/selection, progress indicators and switches (track `primaryInk`, thumb `onPrimaryInk` when on) also draw in `primaryInk` (Material would otherwise use the raw `primary`) — all guarded for every seed and mode in `app_theme_test.dart`.

## Typography

Set once in `AppTheme` (size, weight, line height, tracking only — colour comes from the scheme), so every screen shares one hierarchy. **The font is the platform's own** (Roboto on Android, SF on iOS, each with the OS's Arabic companion): no custom fonts are bundled. An earlier revision of this doc named Inter / IBM Plex Sans Arabic / Noto Sans, but none were ever loaded — the build was always rendering the platform font at stock Material sizes. Bundling a matched Latin + Arabic pair (offline-safe, as assets, not Google Fonts at runtime) is a reasonable follow-up; it is not a precondition for the hierarchy below.

Five working styles carry the redesigned screens:

| Role | `TextTheme` slot | Size / weight | Usage |
|---|---|---|---|
| Page header | `headlineSmall` | 24 / 700, −0.3 tracking | Home greeting/name |
| Card title | `titleLarge` | 20 / 700, −0.2 tracking | Hero lesson title, app-bar titles |
| Section title | `titleSmall` | 15 / 600 | "Today's goal", "Your journey" |
| Body | `bodyMedium` | 14 / 400, 1.45 line height | Arabic support lines, statuses |
| Meta | `bodySmall` 12.5 / 400; `labelMedium` 12 / 600; `labelSmall` 11 / 700 +0.8 tracking | Supporting facts; pills/counts; uppercase overlines |

Overlines go through `overlineStyle()` (`lib/core/theme/overline_style.dart`): in an RTL layout it drops the tracking and adds a point of size, because letter-spacing pulls Arabic's joined letters apart. Upper-casing is a no-op for Arabic. The lesson player's question prompt uses `titleLarge`; the same prompt shown inline elsewhere (answer review, placement) stays `titleMedium`.

**Direction.** Interface copy follows the interface: it is laid out by the ambient `Directionality` and starts at the layout's start edge. Curriculum content does not: an English line is laid out `TextDirection.ltr` and starts at the **left** edge, an Arabic line `TextDirection.rtl` and starts at the **right** edge, in either interface language — each language reads from its own side, and a short line and one that wraps land on the same edge. `ContentText.en` / `ContentText.ar` (`lib/core/widgets/content_text.dart`) is the one way to write such a line (`PhraseText` follows the same rule); never wrap content in `Align(AlignmentDirectional.centerStart)`, which is what put English titles flush right under the Arabic interface. The exception is a label inside a control — an answer option beside its radio mark, a word tile, a level chip — which stays beside its marker. Tested in `test/core/widgets/content_text_test.dart` and, on real screens, `rtl_mixed_direction_test.dart` and `lesson_intro_test.dart`. Curriculum titles embedded in a localized sentence ("Now · Hello, I'm…") are wrapped in Unicode first-strong isolates (`⁨…⁩`, written as escapes — never raw characters in source) so their punctuation doesn't jump when the surrounding sentence is Arabic. Must support text scaling without clipping — Home is tested at 1.0/1.3/1.6×, 320–412px, both directions.

## Spacing scale

`AppSpace`: 4 / 8 / 12 / 16 / 24 / 32 (`xxs`…`xl`) — every gap and padding on the redesigned screens comes from it. Screen gutters 16; 24 between the header and the hero (the one deliberate larger break), 16 between cards. Directional padding/margins throughout, never hardcoded left/right.

## Radii / elevation

- `AppRadius`: 12 (controls, icon tiles, the lesson badge), 16 (cards — also `CardTheme`'s default now), 20 (the hero). Pills are fully rounded. One scale, not a different radius per component.
- Elevation: **one** elevated surface per screen at most — Home's hero has a soft two-layer shadow (light mode) or a hairline border (dark mode, where shadows don't read). Every other container is flat: `card` on `page` is the separation. No M3 surface tint (`surfaceTintColor` transparent on cards, app bars and the nav bar).

## App icon

The launcher icon is a white "M" whose middle forms a speech bubble, rising out of an open book, on a blue-to-cyan diagonal gradient. Its sources live in `assets/icon/` and are not bundled into the app; `flutter_launcher_icons` (configured at the foot of `pubspec.yaml`) writes every platform size from them:

- `app_icon.png` (1024 px, no alpha) — iOS, and Android's legacy square icon below Android 8.
- `app_icon_adaptive_background.png` (1080 px = 108 dp) — Android 8+. The whole artwork sits inside the central 66 dp safe zone, and the outer ring continues the artwork's own edge colours, so a circle, squircle or rounded-square mask never clips the M. The foreground layer (`app_icon_adaptive_foreground.png`) is deliberately empty.

After changing a source, run `dart run flutter_launcher_icons` and commit the regenerated `android/app/src/main/res/` and `ios/Runner/Assets.xcassets/AppIcon.appiconset/` files. The tool (0.14.4) also rewrites `ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS` in `ios/Runner.xcodeproj/project.pbxproj` to `AppIcon`; revert that line, it should stay `YES`.

## Launch screen

Both platforms show the app icon centred on the app's page colour (`AppTokens.page`: `#F5F3F0` light, `#121110` dark), so the native launch screen hands over to the first Flutter frame without a flash.

- **Android:** `res/drawable*/launch_background.xml` over `values/` and `values-night/colors.xml` (`launch_background`); Android 12+ draws its own from the launcher icon and `values-v31/styles.xml`.
- **iOS:** `LaunchScreen.storyboard` shows `LaunchImage` (the icon at 120 pt, with iOS-style rounded corners) on the `LaunchBackground` colour set, which has a dark variant. After changing `app_icon.png`, regenerate the image with `swift tool/ios_launch_image.swift assets/icon/app_icon.png 120 ios/Runner/Assets.xcassets/LaunchImage.imageset`.

## Theming rules

- Light/dark switching mechanism: light / dark / system, user-selectable in Settings (not system-only as originally scoped) — changes apply immediately, no restart, per the app's Settings requirements.
- Colour-theme switching: removed in 1.0.0. One brand accent (`kAppColorSeed`); only light / dark / automatic is a user setting.
- Hard rule: never hardcode a color or use non-directional (`left`/`right`) padding/alignment — always reference a `colorScheme.*`/theme-extension token and use Flutter's directional (`start`/`end`) layout properties, since the UI must mirror correctly between Arabic (RTL) and English (LTR).
