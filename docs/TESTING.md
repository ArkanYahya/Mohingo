# Testing

## Levels & expectations

| Level | Tool | Required for | Coverage bar |
|---|---|---|---|
| Unit | `flutter_test` / `package:test` | Curriculum parsing, content indexing, mastery aggregation, repository logic, Riverpod providers/notifiers | All non-trivial logic — see "What must be tested" below |
| Widget | `flutter_test` (`WidgetTester`) | Individual screens/components, especially bilingual (Arabic/English) and RTL/LTR rendering | Key screens: one representative widget per activity type (all 9, including `dialogue` even though the current bundle has no authored instance), unit/level overview, placement/mission/assessment result screens |
| Integration/E2E | `integration_test` package | Critical end-to-end flows on a real device/simulator | The flows listed below |

## What must be tested

- **Curriculum content:** bundle JSON parsing against the real bundle shape; `schemaVersion`/`contentVersion` validation and graceful failure on an unsupported/corrupted asset (never a raw crash); stable-id indexing and unresolved-reference detection (a lesson/activity referencing a grammar/lexicon/chunk/canDo id that doesn't exist); content catalogue availability state (A1 and A2 `available`, each with a bundle; B1–C2 `comingSoon`, no bundle at all — never selectable as if content exists; the `preview` state, and its promotion to `available` via `MOHINGO_PREVIEW_LEVELS`, is still covered over a fixture catalogue now that no real level is in it — `test/content/catalog/level_catalog_test.dart`, whose A2 expectation is deliberately paired with the release rule below: the snapshot alone would let anyone flip the flag); a level's prerequisite loads first and resolves its earlier-level references, which stay unresolved without it (`course_content_index_prerequisite_test.dart`, `course_content_providers_test.dart` with `test/content/fixtures/minimal_bundle.dart`); a content id's level (`content_level_test.dart`); A2 shapes parse — bilingual word examples, lesson texts, source cards, partner lines (`test/content/models/`).
- **Content gates (`test/content/levels/`):** one suite, every released level. `level_gate_config.dart` holds each level's numbers — unit shape, skill balance, length bands, vocabulary floor, prompt repeats, Can-Do tagging, capstone ids and pass mark — and every gate file loops over `kLevelGates`, so B1 joins by adding a config row, not by writing the rules an eighth time. Where a level genuinely differs it carries a `DeclaredException`: a value plus a written reason, never a skip; `level_config_test.dart` refuses an exception naming a unit that does not exist or carrying no reason, and there is no boolean anywhere in the config that turns a gate off. A1 carries two: U0's shape (5 lessons / 20 activities / 2-5-13, onboarding) and U1's (7 / 30 / 5-7-18, authored before the shape settled), because re-cutting either would move published ids. A1's tags cross skill categories, so its Can-Do rule runs at unit level — every required objective carried by at least one activity of its own skill — which is the property the app's mastery model actually depends on. By file: **structure** (`level_structure_test.dart`) the level's shape with its exceptions, references resolving in the level or its prerequisite, the bundle parsing and indexing, a `prerequisite`-role unit not counting towards the level and every core unit counting; **bilingual** (`level_bilingual_test.dart`) Arabic on every conversation line, prompt, model text, title and taught record, English fields free of Arabic script, Arabic that is not the English copied across; **answerable** (`level_answerable_test.dart`) a source for every mediation task, a transcript for every listening item, a text for every reading question — a drill whose prompt carries its own material (`Complete: I'm ___ Iraq.`) is exempt by its colon, measured before adoption: no A2 reading item has one — partner turns for every interaction task, a graded rubric on every mastery speak/write task (any type the evaluator grades: `keywordChecklist`, `letterSequence`, `numericRange`, `nonEmpty`, with the keyword-specific checks on keyword lists), a closed question with a right answer among its options and a wrong one to pick, every listed word and phrase appearing in its lesson (`{slot}` and `...` are both template notations; a slash card such as `Yes, I can. / No, I can't.` requires each alternative), and no earlier-level sense re-registered; **design limits** (`level_design_limits_test.dart`) skill balance in the level's ranges, every guided lesson opening on 4-8 lines between 2-3 speakers, texts and transcripts inside the unit's band, prompt-repeat and matching caps, Can-Do tagging at the level's granularity, and a `wordGuide` on every free-writing task — keyed on `WriteActivity`, since A1 has sixteen `order`/`form` writing-skill drills a word count means nothing for; **masterable** (`level_masterable_test.dart`) every unit masterable through the real `MasteryAggregationService`, every unit asking for objectives and skill groups it could fail, every skill a unit teaches in at least `minimumEvidencePerRequiredObjective` mastery activities being required (the policy's own threshold — fewer could never back a requirement), and the release rule that reads the catalogue, re-runs the capstone checks and asserts the capstone suite file still exists on disk; **capstones** (`level_capstones_test.dart`, rules in `level_capstone_checks.dart`) both exits of each level, bands and pass mark from the config, unseen inputs. Porting A2's seven files here changed no A2 outcome — 47 tests before, 46 plus the all-pairs shared-id check now in `level_config_test.dart` — and running the result over A1 found roughly 290 content items A2's gates would have rejected, all fixed on 2026-09-22 (see that commit), and **eight rules that were the gate's fault rather than A1's**, every one the same defect this suite has produced before, comparing a cruder key than the rule means: `Skill.writing` for a free-writing task, `keywordChecklist` for a graded rubric, every mode for a taught skill, `TextChoice` for a question about a text, one placeholder notation for a template, a whole slash card for one phrase, lesson granularity for an objective earnable by its own skill, and every unit for one that counts towards the level. A2 contains none of the shapes those keys got wrong, which is exactly why its own suite never showed them.
- **ADR 0005's network boundary (`test/content/online_refinement_boundary_test.dart`):** the one gate in this directory that belongs to no level. It walks every bundle under `assets/content/en/` — discovered, not hardcoded, so a level added later is covered the day its file lands — and fails if any `speak` task carries `evaluation.onlineRefinement`, naming the activity, its lesson and its bundle. `SpeakActivityView` honours the mark on whatever carries it, so such a task queues the learner's **recognised speech** for the public LanguageTool API, which [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md) rules out by name. A2's authoring marked 120 of them; `1893e23` unmarked them before release and nothing would have caught it, because the rule lived only in an ADR. Two vacuity guards: at least two bundles must be found, and at least one `speak` task.
- **Mutation-proving a content gate.** Every gate above was written by breaking the content so it *should* fail, running it, confirming it failed and named the offender, and reverting. Do the same for the next one: five gates on this branch were found fakeable after being written, and the ones that survived review were the ones somebody had tried to break. A gate asserted but never broken is the defect this project has produced most often.
- **Progress & mastery:** DB migrations; progress resume after app termination mid-lesson (no duplicate or lost `activity_attempts`); practice-vs-mastery separation (`mode='practice'` activities never count as mastery evidence); Can-Do evidence aggregation per `(canDoId, evidenceSkill, mode)` against `MASTERY_POLICY` (minimum evidence count, minimum score, no single compensating average across required skill groups) — see [DATA_MODEL.md](DATA_MODEL.md); a Unit's "recommended next" resolution never behaves as a hard lock (a learner can navigate to any unit); "you are here" (`currentUnitId`) resolves per level — progress recorded in a different level never moves the position shown in this one (`current_unit_selector_test.dart`).
- **Published id stability (`test/content/published_id_stability_test.dart`):** a level's ids are permanent once it ships, its activities' `mode` frozen and their `canDo` append-only — checked against `test/content/published/<level>-published-ids.json`, the committed record of what shipped. Three directions, and all three are load-bearing: **stability** (nothing published may be removed, re-moded or un-tagged), **completeness** (the snapshot must name every id the bundle now publishes, or content added later sits outside the guard with nothing failing), and **version** (the snapshot's `contentVersion` must be the bundle's, which catches a hand-edited snapshot or a bundle bumped without regenerating). The completeness check deliberately phrases its own failures rather than reusing the stability messages — "was published and is gone" is exactly backwards for an id the bundle has and the snapshot does not. The rule that new ids may not appear under an unchanged `contentVersion` lives in `tool/update_published_ids.dart`, the only place that sees both the old snapshot and the new bundle; the completeness check is what forces the script to be run at all. All five failure modes were mutation-proved: a deleted activity, a changed mode, a dropped tag, an added activity, and an addition without a version bump.
- **Content versioning and stale units:** the stale-unit rule is a pure function tested as data (`content_drift_test.dart`) — content that only *grows* must flag nothing, and only a unit the learner actually worked in may go stale. The queries behind it are tested against a real database (`content_staleness_queries_test.dart`): flagging clears the flag on the learner's other units, a mastery recompute never clears it, one learner's flags never touch another's, and `latest()` breaks an `installedAt` tie by `id`. The end-to-end behaviour is tested **against a real prior-version snapshot, never a fresh install** (`content_staleness_test.dart`): a fresh install has no previous row, so every diff is empty by construction and a suite built on one would pass while the feature did nothing. Seed a `content_versions` row holding the shipped bundle's real ids plus one that has since been retired, then load the real bundle — the same shape as `database_test.dart` testing migrations against a hand-built previous schema rather than `onCreate`. Three of those tests fail if the `latest()`/`recordIfNew` ordering is reversed, which is the one mistake that leaves this feature dead with a green suite; that mutation was run and observed. On the UI side, a unit that did *not* drift must say nothing (`course_screen_test.dart`) — without that negative, an implementation that puts the line on every unit passes just as well.
- **Levels:** the current level resolves to the enrolment with the most recent `lastSelectedAt`, falling back to the base level when none is set or a pre-v5 row has no `levelId` (`level_access_test.dart`, `level_providers_test.dart`); a level's access (`open`/`lockedNeedsPrerequisite`/`notReleased`/`noContent`) is exercised for every combination of availability, prerequisite completion and unlock state; selecting or unlocking a level writes the enrolment (`drift_learner_repository_test.dart`); browsing a level (the Learn tab's read-only preview) never enrols in it and never changes the current level (`course_screen_test.dart`). Every screen that follows the current level is tested with a learner actually in A2, not only in A1 — Words & phrases and Grammar (`vocabulary_list_screen_test.dart`, `grammar_screens_test.dart`) each assert that an A1 learner gets A1's registry, an A2 learner gets A2's, filtering to A1 gets A1's back *grouped under A1's own units*, and that filtering leaves `currentLevelIdProvider` untouched — the last being the assertion that a level filter must never quietly become a level switch. Grammar additionally asserts no section is ever headed "Unit 0", which is what a lesson id resolved against the wrong level would produce. `pumpVocabulary`/`pumpGrammar`/`pumpReview` take a `currentLevelId` and stand both real bundles up over `twoLevelTestCatalog` (`review_test_harness.dart`, which also owns `reviewTestA2Index` and `seedCurrentLevel`). The Review tab is tested against the **opposite** rule, since it deliberately follows no level (`review_across_levels_test.dart`): a learner in A2 with items in both levels sees them in one count and reviews them in one session; weak spots arrive from every level with a unit in progress, each labelled with its own level; the browse tiles count every level reached. Two assertions there are load-bearing — that the due count is exactly the session's total, which is the disagreement release exposed, and that a level whose bundle fails to load (`pumpReview(a2Fails: true)`) leaves the other level's items both counted and reviewable rather than taking the tab down.
- **Placement/mission/assessment:** placement classification-boundary tests confirming all four actionable outcomes are reachable and the test never claims a level the app has no content for; the block split for both shipped levels (A1's 13 units become U0-U3, U4-U6, U7-U9, U10-U12; A2's 12 become U1-U3, …) and the block/unit pass rules that go with it; a unit numbered inside **its own** level, so a result never resolves to "Unit 0" against the level on screen; one end-to-end pass per learner profile against the real A1 and A2 bundles — a complete beginner (7 questions, recommended `A1-U0`), a learner with a gap inside A2 (25, drilled down to `A2-U5`), and one who answers every block correctly (25, "A2 looks mastered", stored `a2Mastered`) — which needs `enterWrongAnswer` alongside `enterCorrectAnswer` in `test/features/activity_engine/answer_activity.dart`, since only a wrong answer makes the scan stop anywhere; "Start at …" making that level current, unlocking it and opening the unit; a stored `a1Mastered` row still rendering in history; final-assessment/mission isolation from ordinary training (their attempts never surface through Review, their prompts are never drawn from practice content); retake attempts stored separately from the original; the Final Mission and Final Assessment are actually completable end to end against the real bundle — every writing/speaking/mediation rubric graded via `evaluate()` on a plausible correct answer, fed through `FinalMissionScoring`/`FinalAssessmentScoring` exactly as their screens do, asserting an overall pass (a `form`-type activity's `notAutoGraded` submission must be excluded from that scoring evidence, never left in as a permanently-pending item — see [DATA_MODEL.md](DATA_MODEL.md)).
- **Vocabulary/Grammar:** vocabulary review-scheduling algorithm (whatever documented spaced-review algorithm is chosen); two lexical senses sharing a headword are treated as distinct records (e.g. the bundle's `A1.LEX.PICTURE.N01`/`N02`); marking a vocabulary item confident/reviewed or a grammar item reviewed never flips the related Can-Do's mastered state.
- **Speech:** speech-unavailable and permission-denied fallback to the typed-answer path; a `speak` activity answered via that fallback never records speaking evidence (`evidenceSkill='writing'`, `wasFallback=true` — see [DATA_MODEL.md](DATA_MODEL.md)); no verbatim transcript is persisted after scoring.
- **Online-refinement feedback:** `WriteActivityView`/`SpeakActivityView` must flip from the pending banner to the real Correct/Incorrect result the moment a matching resolved `activity_attempts` row appears — via `latestAttemptProvider`, invalidated by `pendingRefinementDrainerProvider`'s `onItemResolved` — without the learner leaving or re-entering the activity; a resolved row from an *earlier* retry of the same activity must never be shown as this submission's result. Watch for the whole-second precision trap: `attemptedAt` is stored at whole-second granularity, so a millisecond-precision "submitted at" capture must be truncated to seconds before comparing, or a result written in the same wall-clock second as submission gets wrongly treated as stale (see `write_activity_view.dart`'s `_truncatedToSeconds`).
- **Lesson answer review (Learn tab only):** reopening a lesson that has reached its final activity shows `LessonReviewScreen`, not `LessonPlayerScreen` — a lesson that's merely started or mid-way through is unaffected. Every answerable activity view's `reviewAttempt` parameter renders read-only, seeded from the recorded `ActivityAttempt`, and must **never** call `evaluate()` or otherwise recompute correctness/score — the banner always reflects the attempt exactly as recorded, even when it disagrees with what live re-grading of the same answer would produce (a rubric can change after the attempt was recorded). A `notAutoGraded` (never-graded) attempt — `ActivityAttempt.isCorrect` stored as `null`, not `true`/`false` — must render as the neutral "saved for review" treatment in review mode too, exactly like a live `notAutoGraded` submission, never as incorrect. A lesson replayed more than once shows only the latest attempt per activity, and reopening the review screen after a "Practice again" replay reflects that latest attempt, not stale pre-replay data. Out of scope: the Tests tab (Final Mission/Assessment/Placement Test) — a deliberately separate, later decision, see docs/superpowers/specs/2026-09-09-lesson-answer-review-design.md.
- **Select, then Check (every activity type):** tapping an option, placing a word or pairing an item never grades anything — nothing is submitted, graded, coloured or sounded until Check, so a mis-tap can be fixed; tests assert both halves (no submission after the tap, the result after Check). Matching pairs look neutral before Check (never green). Inside the lesson player (`ActivityFrameScope`) the feedback slot must render the pinned `ActivityCheckBar` and then the `ActivityFeedbackPanel` (whose Continue calls the player's `onContinue`), never the inline banner or a modal sheet; every other host keeps the inline Check button and `ActivityFeedbackBanner`. End-to-end tests drive real content through `answerCheckAndAdvance()` in `test/features/activity_engine/answer_activity.dart` (answer → Check → Continue/Next) rather than per-file copies. A lesson with an encounter conversation opens on its intro, so player tests that start such a lesson from the beginning call `passLessonIntro()` (`test/features/lesson_player/lesson_player_test_helpers.dart`) first — explicitly, never hidden inside the answer helper.
- **Learn tab:** it opens on the course (title in both languages, units mastered, every unit); the unit being worked on is the one highlighted card with its lessons done, next lesson and a Continue button into the player (Start lesson / "Start here" for a new learner); mastered, not-started and starter units say so; each unit node is announced with number and state; units open their unit page, the finish card opens Tests; the level switcher carries every level with content (A1, A2) — the learner's own level filled, an open level tappable to switch, a locked level's tap opening the lock sheet with a way forward (the placement test or opening it anyway) or, for a not-yet-released level, only a way to browse it read-only — while B1–C2 have no segment at all, just a caption that more levels are coming. Browsing an unreleased level never marks it as the learner's own, shows no current-unit card and no finish card, and returns to the learner's own level on tap. Old addresses (`/learn/<level>`, `/learn/<level>/unit/<id>`) redirect to the new ones.
- **Lesson complete:** the ring shows right ÷ auto-graded answers and announces the tally; answers saved for review are counted apart and, when nothing was graded, there's no accuracy figure; the third figure falls back from phrases to questions; skills are listed once each with both speaking skills as "Speaking"; the next lesson is previewed and both it and Next lesson continue, the last lesson offers Back to unit; Review answers replaces the player with the review route; figures stack on a narrow screen at large text; and a lesson finished in a later sitting sums up every activity, not only the ones answered in that sitting.
- **Lesson intro:** a lesson with a conversation opens on it (every line, speaker and Arabic; read aloud once, in order; a tapped line alone), the Arabic switch hides/shows every Arabic line, key phrases follow (NEW only on phrases introduced in this lesson, grammar forms), "Start practice" reaches the first question, the intro is the progress bar's first group, a mid-lesson resume skips it (counted as done), a lesson without a conversation starts on its first question, and a speaking question's useful phrases stay hidden until asked for — all against real content (`lesson_intro_test.dart`). A lesson built around a text opens on it (title, English, Arabic behind the switch), then key phrases; key phrases mark earlier-level items From A1 (`lesson_key_phrases_step_test.dart`). `DeviceTextToSpeechService` must turn on completion-awaiting and time out rather than hang (`device_text_to_speech_service_test.dart`). `ChoiceActivityView`/`GapActivityView` render their options in a freshly shuffled order on every mount (not the bundle's raw JSON order, where the real A1 content puts the correct answer first 95% of the time), stable across the same instance's own rebuilds. `ChoiceActivityView`'s audio transcript auto-plays on mount for a live instance, never in review mode (a review screen can show several at once). A correct/incorrect feedback sound plays for every live submission across all activity types except a `notAutoGraded` result (nothing to celebrate or flag) and never in review mode (nothing was just submitted) — see `SoundEffectsService`/`playFeedbackSoundSafely` below.
- **Question material:** a reading question shows its text, left to right, in test mode too; mediation tasks show their source card; a speaking task's partner lines show and are read aloud in order on opening, and can be replayed, but never auto-play in review.
- **Localisation/theming:** Arabic/English locale and RTL/LTR rendering correctness for any screen carrying bilingual content, including mixed-direction text (an Arabic sentence with an embedded English word/phrase must not force the embedded text into RTL); light/dark/system theme and colour-theme selection persist across restarts and apply immediately without one.
- **Offline:** at least one full end-to-end "complete an A1 unit" flow in airplane mode, covering onboarding (local profile creation) → guided path → a lesson → an activity of each broad type → unit state updates, all without any network connectivity.

## Platform services that must be faked

Device-backed plugins have no platform channel to answer in `flutter test`, so any test that reaches one must override its provider with the matching fake — otherwise the test hangs waiting for a reply that never comes, or throws `MissingPluginException`:

- **Speech** (`flutter_tts`, `speech_to_text`, `permission_handler`): override `textToSpeechServiceProvider`/`speechRecognitionServiceProvider`/`speechCapabilityServiceProvider` with `test/features/speech/fake_speech_services.dart`'s fakes for any widget that reads them.
- **Connectivity** (`connectivity_plus`): override `connectivityServiceProvider` with `FakeConnectivityService` (`test/features/activity_engine/fake_connectivity_service.dart`) in **every test that pumps the full `MohingoApp`**, not only tests about online refinement. `MohingoApp` watches `pendingRefinementDrainerProvider` at root, which listens to the real `DeviceConnectivityService`'s platform channel; unmocked, the plugin reports an unhandled `MissingPluginException` on both listen and cancel. `test/widget_test.dart`'s shared pump helper already does this — reuse it rather than re-deriving the override list.
- **Grammar check** (the LanguageTool HTTP call): no test ever makes a real network request. `FakeGrammarCheckService` (`test/features/activity_engine/fake_grammar_check_service.dart`) stands in with a canned result, a canned `GrammarCheckUnavailableException`, and an optional artificial `delay` for exercising overlapping drains. Overriding `grammarCheckServiceProvider` is only needed when the queue actually has rows — an empty `pending_online_refinements` table never reaches the service.
- **Sound effects** (`audioplayers`): unlike the three above, leaving `soundEffectsServiceProvider` unoverridden is always safe — `playFeedbackSoundSafely` (`lib/features/activity_engine/domain/sound_effects_service.dart`) is fire-and-forget and swallows any failure, the same rationale as `PendingRefinementDrainer.triggerDrain()`, so an unmocked platform channel never hangs or fails a test. Override it with `FakeSoundEffectsService` (`test/features/activity_engine/fake_sound_effects_service.dart`) only when a test needs to assert on which sound played.

## Performance

No real device or profiler (DevTools timeline, frame-rendering stats, memory snapshots) is available in this dev environment, so frame-rate/jank/memory profiling has not been done — flag this explicitly rather than claiming a performance bar was verified when it wasn't. What has actually been checked:

- **Content parsing/indexing time**, the one cost proportional to the curriculum bundle's size (A1 is 820KB, ~1,200 leaf records; A2 is 1.2MB and has never been measured, though it loads lazily and off the UI isolate the same way, and only when a learner opens or browses it): measured directly (`CourseBundleParser.parse` + `CourseContentIndex.build`, JIT-warmed) at ~9ms total on this dev machine's Dart VM — not a real phone, and not a first-run (un-warmed) number, but a strong signal this isn't a performance risk even accounting for slower mobile hardware, especially since it already runs off the UI isolate via `Isolate.run` (see [ARCHITECTURE.md](ARCHITECTURE.md)) so a slower result would show as a longer splash screen, never a janky frame.
- **No obvious anti-patterns** (rebuilding a whole screen from a single-field state change, an unbounded list with no lazy building, a synchronous DB call on the UI thread) were introduced — Drift's async API and Riverpod's provider-scoped rebuilds are used throughout as intended.

Real profiling (startup time to first frame, scroll jank in the longest lists, memory under a full A1 session) should be one of the first things done once a real Android/iOS device or emulator is available — see the real-device-testing limitation noted throughout this doc and [TECH_STACK.md](TECH_STACK.md).

## What doesn't need tests

- Generated code (Drift schema/DAOs, `freezed`/`json_serializable` boilerplate)
- Trivial getters/simple data classes with no logic
- Third-party package wrappers with no added logic (e.g. a thin call to `speech_to_text`)

## Curriculum package validators (separate from the Flutter test suite)

Both authoring packages (`reference/a1-modular-course/`, `reference/a2-modular-course/`) are behind their shipped bundles and carry an `OUT_OF_DATE.md` saying so; A2's whole level was written in the shipped asset, so its package's `dist/` is the skeleton the gates exist to reject. A1's: the authoring pipeline lives in `reference/a1-modular-course/` and is **behind** the shipped bundle — content fixes since 2026-09-08 were made in `assets/content/en/A1/a1-course-bundle.json` directly (see [ARCHITECTURE.md](ARCHITECTURE.md), "Content"). Its Node-based validators check the *authoring* side (units/registries), not the Flutter app; only run its build after porting those fixes back, or it will overwrite them. In the app, `test/content/a1_content_quality_test.dart` checks the shipped bundle for learner-visible slips: Arabic in an English `prompt`, authoring notes in a grammar `meaningAr`, choice options that are internal keys (not words, and not a picture with a media specification), and — since every lesson text now renders — that every lesson's `readingText.textAr` carries its whole Arabic, not a truncated stub.
