# Architecture

## Overview

Mohingo is an offline-first Flutter mobile client (iOS + Android). Every learning feature runs on the device against a local database; the only backend is Firebase, used for **optional** sign-in and for copying a signed-in learner's progress between their devices ([ADR 0010](adr/0010-optional-accounts-and-progress-sync.md), which superseded the "no backend at all" of [ADR 0004](adr/0004-local-only-v1-no-firebase-backend.md) for accounts and sync). Separate, non-shipped dev-time curriculum packages (`reference/a1-modular-course/`, `reference/a2-modular-course/`) produced each level's first runtime bundle, which was copied into the Flutter app as a bundled asset — not downloaded from anywhere. Both are now behind the app: content is authored in the shipped assets themselves and held to its design by the `test/content/` gates (see "Content" under Key flows). Content is still never downloaded ([ADR 0004](adr/0004-local-only-v1-no-firebase-backend.md)'s bundled-asset decision stands); Cloud Storage is unused.

## Layers / boundaries

```
UI (widgets)
  -> state (Riverpod providers/notifiers)
    -> repository layer
      -> local data (Drift/SQLite) — progress only, the source of truth for what the app renders
      -> sync layer (features/sync) — background only: uploads the local outbox and merges
         downloads into Drift; nothing on screen waits on it
        -> remote data (Firestore) — a signed-in learner's copy of their progress
           (see "Repositories and sync" below)
```

A separate, third data source sits alongside the two above: **bundled curriculum content** (`lib/content/`), loaded once from a Flutter asset and held in memory — never mirrored into Drift. See "Content module" below.

A separate **speech service** is called directly from lesson-player/vocabulary/grammar features via its own DI-bound interface — it doesn't go through the repository/data layers since it's a device capability, not persisted content. `TextToSpeechService.speak(text, speaker:)` is bound to `BundledAudioTextToSpeechService` ([ADR 0008](adr/0008-bundled-pre-generated-speech-audio.md)): it looks the text up in `AudioClipIndex` — every released level's `assets/audio/en/<LEVEL>/manifest.json`, merged at first use, keyed by a normalised-text hash and a role (`_` teacher, a dialogue speaker label, `partner`) — and plays the clip through `ClipPlayer` (`audioplayers`) at a playback rate derived from the learner's speed preference; text with no clip, or an index that failed to load, goes to `DeviceTextToSpeechService` (`flutter_tts`). Either way `speak()` completes when the audio *finishes* (or fails, or is stopped), not when it starts, and both paths cap a play with a length-based timeout so an engine that never reports can't hang a caller. The lesson player's conversation relies on this to read lines in sequence, each in its own character's voice. What the app speaks is enumerated once, in `lib/content/audio/speakable_strings.dart`; the level gate holds each manifest to that list, and `tool/audio/` (Python, dev-time only) generates the clips from the same list.

Rules for crossing layers:
- UI never talks to Drift, the content asset, Firebase Auth or Firestore directly — always through a repository or the content-index provider. This keeps local-vs-remote swappable and the UI testable against a fake repository.
- The local database (Drift) is the source of truth for *progress*; the parsed content bundle is the source of truth for *curriculum content*; the two are never merged into one store, and Drift only ever references the bundle's stable string IDs (never duplicates bundle content).

```
lib/

                    #   media (diagram renderers for the curriculum's structured scene types),
                    #   shared widgets (loading/empty/error/unsupported-content states), utils
  content/         # bundled curriculum ONLY — read-only, never mutated, never imported by data/local,
                    #   and never importing from lib/features/ (it is a foundational layer *under*
                    #   the feature layer; anything a feature needs from it flows one way only)
    models/          # typed immutable models (freezed) for the bundle's shape: units, lessons,

    audio/           # every string the app speaks and the role it is spoken in
                      #   (speakableStringsOf) — read by the audio gate; mirrored by tool/audio/,
                      #   the Python tool that generates the bundled clips (ADR 0008)
    providers/       # Riverpod providers exposing the loaded bundle + index, kept alive app-lifetime
  data/
    local/           # Drift schema (progress tables only), DAOs, migrations
    remote/          # empty — the cloud store lives with its feature (features/sync/data/)
  features/
    <feature>/

      application/   # Riverpod providers/notifiers
      domain/        # entities, business rules
      data/          # feature-specific repository implementations (local-backed; Firebase only
                      #   in features/account/data and features/sync/data)
    account/         # sign-in: AuthRepository (Firebase Auth + Google + Apple behind it), the account
                      #   session (which local learner is on screen), sign-in/forgot-password screens
    sync/            # progress sync: SyncRecord schema + merge rules (domain, no Drift/Firebase),
                      #   DriftLocalProgressStore (outbox → records, records → rows),
                      #   FirestoreProgressStore, SyncController (when to run)
    activity_engine/ # … domain/evaluation/: the evaluator, grading_signals (combineSignals),
                      #   MeaningSignalService + LocalJudgementService interfaces, the WordPiece

```

`tool/meaning/` (Python, dev-time only) checks model answers against their rubrics and rebuilds the bundled embedding model; `assets/models/` holds that model and its vocabulary. `tool/ai_pack_spike/` (Flutter, dev-time only) is the ADR 0013 Phase B device spike: a separate package with its own `pubspec.yaml`, workflow and tests, excluded from the root analyzer, that runs candidate language models on a phone and reports memory, speed and judgement quality — nothing in it is imported by `lib/`.

Feature areas: `app_shell, onboarding, learning_path, lesson_player, activity_engine, vocabulary, grammar, review, placement_test, final_mission, final_assessment, progress, speech, settings`. Which levels exist and are available is the app-owned catalogue in `lib/content/catalog/level_catalog.dart` (`kLevelCatalog`), kept distinct from `learning_path` (the course and unit pages, level-agnostic) — this split is what made adding the A2 bundle purely additive, with zero changes to A1 code. The Learn tab (`/learn`) opens on the learner's current level (`CourseScreen`, `currentLevelIdProvider` — see "Current level and level lock" under Key flows); units are at `/learn/unit/<id>`. There is still no separate level-list screen — instead, a `LevelStrip` segmented switcher sits under the course title for every level that has content (A1 and A2 today; a level with no bundle, like B1-C2, is never a segment, only a caption saying more are coming) — and the old addresses `/learn/<level>` and `/learn/<level>/unit/<id>` still redirect (`legacyLearnRedirect`). See [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md)'s Level switcher/Level lock sheet/Level preview entries for what the learner actually sees.

## Repositories and sync

Every progress repository still reads and writes only Drift — none of them knows sync exists. Sync is added *beside* them ([ADR 0010](adr/0010-optional-accounts-and-progress-sync.md)):

- **Capture:** SQLite triggers (`AppDatabase.syncTriggerStatements`) append `(table, rowId, learnerId)` to `sync_outbox` on every insert or update of a synced table. No repository calls anything to make that happen.
- **Upload:** `SyncEngine` reads the outbox, `DriftLocalProgressStore` turns entries into `SyncRecord`s (plain Dart maps, schema in `sync_records.dart`), `FirestoreProgressStore` writes them (append-only records by batch; mergeable ones merged with the server copy in a transaction), and only then are the entries deleted.
- **Download:** per collection, documents written after a saved cursor; `DriftLocalProgressStore.applyRemote` merges each into its local row by natural key (`mergeRecords`) and removes the outbox entries the apply itself caused.
- **Derived state:** `unit_progress` isn't synced; when answers arrive from another device `SyncController` re-runs `MasteryAggregationService` for every unit with evidence, then invalidates the learner's providers (`refreshLearnerProgress`).
- **Ownership:** `learners.firebase_uid` binds a learner row to an account; `AccountSessionController` decides which learner is active (guest, the account's own, or — on a first sign-in over guest progress — asks), and `currentLearnerProvider` follows it. The engine refuses a learner not bound to the signed-in account.

Only `features/account/data/firebase_auth_repository.dart` and `features/sync/data/firestore_progress_store.dart` import Firebase. Without Firebase configuration the auth repository is `UnavailableAuthRepository`, the cloud store is null, and the app is exactly the local-only app of v1.

## Key flows

**Content (author → learner, v1):** the A1 bundle was first produced by the dev-time curriculum pipeline, now kept in `reference/a1-modular-course/` → LLM drafts lesson content → author reviews/edits → curriculum's own validators/build tool (`validate-a1.mjs`, `audit-quality.mjs`, `build-a1.mjs`) produce `dist/a1-course-bundle.json` → that file is copied verbatim into the Flutter project as an asset (`assets/content/en/A1/a1-course-bundle.json`) → at app startup, parsed once off the UI isolate, `schemaVersion` validated, indexed into `CourseContentIndex` → lessons render from that in-memory index. No network call is involved anywhere in this flow after the app is installed. **Where to edit content now:** since 2026-09-08 every content fix (structured `EvaluationSpec`s, mission fixes, and the 2026-09-19 prompt/option/meaning fixes) has been made directly in `assets/content/en/A1/a1-course-bundle.json`, and the pipeline's own `dist/` copy was never updated. The shipped asset is therefore the source of truth: edit it directly, keep `test/content/a1_content_quality_test.dart` and the `a1_*_regression_test.dart` files green, and never rebuild it from `reference/` without first porting those fixes back.

**A2 took the same shape, deliberately.** `reference/a2-modular-course/` was imported once into `assets/content/en/A2/a2-course-bundle.json` and then never consulted again as a source: the level was written unit by unit *in that asset*, because what the generator produced parsed but could not teach (one-line conversations, no present perfect anywhere, 120 productive tasks whose `evaluation` parses to `null`). The reference now carries its own `OUT_OF_DATE.md`, and rebuilding from it would undo the whole level. What holds the shipped file to its design is `test/content/levels/` — one suite over every released level, per [ADR 0007](adr/0007-one-standard-for-every-level.md) and [LEVEL_STANDARD.md](LEVEL_STANDARD.md); see [TESTING.md](TESTING.md); a level cannot be marked `available` in the catalogue until those gates cover every unit and both capstones. Expect the same for B1: import, then author in the asset under gates. (Deferred, post-v1: replacing the "copied at build time" step with a Firestore-hosted download-on-launch step, per [ADR 0001](adr/0001-offline-first-firebase-only-backend.md)'s original longer-term direction.)

**Levels and earlier-level references:** `levelCatalogProvider`/`bundleAssetLoaderProvider` (overridable in tests) feed `courseContentProvider(levelId)`; a level with a `prerequisiteLevelId` is indexed with the earlier level's index attached, and `resolveGrammar`/`resolveLexicon`/`resolveChunk` look there after the level's own records (the `*ById` maps hold each level's own records only). `contentIndexForIdProvider(contentId)` gives any screen that opens one unit, lesson, word, phrase or grammar point the index of that item's own level via `levelIdOfContentId`, rather than the hard-coded `'a1'` every such screen used before. See [ADR 0006](adr/0006-multiple-levels.md).

**Current level and level lock:** the level a learner is working in is `currentLevelIdFor` (`lib/features/progress/domain/level_access.dart`) — the `course_enrolments` row with the most recent `lastSelectedAt`, or `kBaseLevelId` when none is set (a row written before schema v5 has a null `levelId` and is read, and later backfilled, as the base level too). It lives in the progress database, not `shared_preferences`, specifically so "Reset progress" (which deletes every `course_enrolments` row for the learner) returns them to the base level rather than leaving a stale current-level preference behind. `levelAccessFor` classifies each catalogue entry into `open`/`lockedNeedsPrerequisite`/`notReleased`/`noContent` for a given learner: a `comingSoon` level (no bundle) is `noContent`; a `preview` level (content loads, lessons don't) is always `notReleased` regardless of enrolment; an `available` level with no prerequisite, or whose prerequisite is complete, or that the learner has explicitly unlocked (`markLevelUnlocked`), is `open`; otherwise it's `lockedNeedsPrerequisite`. Since A2's release that last branch is the live one: A2 is `available` with `prerequisiteLevelId: 'a1'`, so it reads `open` for a learner who has mastered every A1 unit that counts (`levelComplete`) or has tapped "Open A2 anyway", and `lockedNeedsPrerequisite` — sheet, not wall — for everyone else. No level is `preview` today. The Learn tab's `LevelStrip` renders every switchable level (everything but `comingSoon`), and `showLevelLockSheet` explains a non-`open` tap: a level the learner hasn't reached offers the placement test or "Open anyway" (`LevelSelectionController.unlock` then `.select`); a level that isn't released yet offers only to browse it read-only (`CourseScreen`'s `_browsingLevelId`, cleared by "Back to A1") — see [ADR 0006](adr/0006-multiple-levels.md) decision 4 and [UX_PRINCIPLES.md](UX_PRINCIPLES.md). Browsing never touches the enrolment: `LevelStrip`'s filled segment always reflects `currentLevelIdProvider`, never the level the page happens to be showing, and `MohingoApp` only ever enrols the learner in `currentLevelIdProvider`'s level (fire-and-forget, at the root), never in a level being merely browsed. A level's bundle loads lazily — the first time something watches `courseContentProvider(levelId)`, whether that's opening it, selecting it, or just browsing it — never eagerly for the whole catalogue; the router's content gate (`app_router.dart`) only ever waits on `courseContentProvider(kBaseLevelId)`, so a later level that's slow or fails to load never blocks startup. (A development build can promote a `preview` level straight to `available` with `--dart-define=MOHINGO_PREVIEW_LEVELS=a2`, so the product owner can walk through its real lessons — see `applyPreviewOverrides`.) `currentUnitId` ("you are here" on the Learn spine and Home's Continue card) is computed **per level**: it only counts `lesson_progress` rows whose `unitId` belongs to the level being shown, since a learner can hold progress in more than one level at once and a unit id from a different level must resolve to nothing in this level's index.

**What follows the current level, and what doesn't:** Home, the Learn tab, the Tests tab, the two capstones and the two browsable registry lists do. `CourseScreen` watches `courseContentProvider(shownLevelId)` inline, because it also has a level the learner is merely *browsing*, which is not their enrolment. `HomeScreen`, `TestsHomeScreen`, `FinalMissionScreen` and `FinalAssessmentScreen` have no such second notion, so they share one seam instead: `currentCourseProvider` (`features/progress/providers/level_providers.dart`) resolves `currentLevelIdProvider` → `courseContentProvider(levelId)` into that level's `CourseContentIndex` **and** its CEFR code, collapsing the two watches into one `AsyncValue` so each screen keeps a single loading/error branch. Every screen that opens one *item* — unit overview, lesson player, lesson review, word/chunk/grammar page, quick practice, the refinement drain — resolves its own level from the id via `contentIndexForIdProvider`. So a learner who switches to A2 gets A2 units, A2 lessons, A2 word pages, and A2's Final Mission and Final Assessment.

**Review is the deliberate exception, and it is not an oversight.** The Review tab follows *no* level: it shows every level the learner has reached at once, because a learner who moves to A2 must keep meeting A1's words in spaced review — that is the moment they need them most, and it is why [ADR 0006](adr/0006-multiple-levels.md) rejected separate courses per level outright. `reviewContentProvider` builds a `ReviewContent` (`features/review/domain/review_content.dart`) holding one `CourseContentIndex` per level the learner is enrolled in (plus `kBaseLevelId`, where everyone starts, and their current level), and every lookup on it resolves against the index of the level the item's own id names — the same rule `contentIndexForIdProvider` applies, since only that keeps an A1 word filed under A1. The level set comes from the enrolments rather than from the item rows themselves, so rating a card doesn't rebuild the tab for a set that cannot have changed. Each level loads on its own inside a `try`, so a bundle that fails leaves its items out of the counts and the session *together* instead of failing the tab: a learner with A1 and A2 items still reviews the ones that resolve. The due card and `ReviewSessionScreen` both render `reviewCardsFor`'s list, which is the structural reason the number on the tab can no longer disagree with the session it opens.

`VocabularyListScreen` and `GrammarListScreen` sit with `CourseScreen` rather than with Home: each has a level the learner is merely *looking at*, so each watches `currentLevelIdProvider` and `courseContentProvider(shownLevelId)` inline, with a `LevelFilterChips` row (`core/widgets/`) over the catalogue's non-`comingSoon` entries. They open on the current level and can be filtered to any level with content — an A2 learner must still reach A1's words and forms, which are in spaced review and turn up in A2's texts — and the filter **never** calls `LevelSelectionController.select`: looking at another level's registry is a view, exactly as browsing is on the Learn tab. Both screens read the units, the lesson ids and the registry records from that one index, so a form is always grouped under its own level's unit numbering; the ids on the rows already carry their level, so a row still opens through `contentIndexForIdProvider` whichever level is on screen. The level row deliberately sits *outside* the content's loading/error branch, so a level whose bundle fails to load doesn't strand the learner on an error page with no way back.

Home adds one thing on top of that seam, and it is the only place in the app that proposes a *change* of level: once the current level's units are all mastered (`levelComplete`) and the level that builds on it (`nextLevelEntryIn`, in the catalogue) is genuinely open (`levelAccessProvider` → `LevelAccess.open`), Home renders a `NextLevelCard` that calls `LevelSelectionController.select`. It is a card the learner taps — Home never switches level on its own, for the same reason the Learn tab's lock only recommends: which level you are in is the learner's decision.

**Placement belongs to no level**, and is the one screen that deliberately doesn't follow the current one: it watches `placementPlanProvider`, which builds a `PlacementPlan` over *every* released catalogue entry (`LevelAvailability.available` with a bundle), in catalogue order. A level whose bundle fails to load is dropped from the plan rather than failing the test, the same way the router's gate lets a later level fail without blocking the app. The Tests tab reads a stored result back through that same plan (`plan.locate(unitId)`), so a recommended unit is numbered against the level **its own id names** — the bug class that once rendered "Unit 0" when an A1 result was resolved against A2's units. No ARB string hard-codes a level name: every string that names one takes a `{level}` placeholder, including the four placement ones, `reviewWeakSpotMeta` and `settingsProfileMeta` (Settings), which was the last of the twelve and was fixed by `fc8fe56`. `grep -rn "courseContentProvider('a1')" lib/` is empty in `lib/features/` — see [ROADMAP.md](ROADMAP.md) and [ADR 0006](adr/0006-multiple-levels.md).

**Content updates and stale units:** each time the current level's bundle loads, `recordContentVersionAndFlagDriftProvider` (`features/progress/providers/content_version_providers.dart`, fired from `app.dart` beside `ensureLevelEnrolmentProvider`) records that version's id snapshot in `content_versions` and, on an *upgrade*, diffs the new bundle against the recorded one. A unit is marked `unit_progress.isContentStale` when the learner has an answer against an activity that is gone, or when the unit's required objectives have moved; the Learn tab's unit row then says so, and nothing is blocked. The diff itself is a pure function (`features/progress/domain/content_drift.dart`) with no Drift and no Riverpod in it.

The hook cannot live in `courseContentProvider`, which is the obvious place for it: `lib/content/` never imports `lib/features/`, and this needs the learner, their attempts and their progress rows. So the content layer stays ignorant of who is reading it, and the progress feature owns the moment a bundle becomes *this learner's* content. Two orderings inside it are load-bearing and both are commented where they are written: `latest()` is read before `recordIfNew` (reversed, the previous snapshot is the row just written and every diff is empty), and a removed activity is placed in its unit through the learner's own `activity_attempts.lessonId` rather than through the bundle, which no longer contains it.

**Vocabulary review (learner, v1):** when a lesson finishes, `LessonPlayerScreen` enrolls the lesson's `lexicon` and `chunks` into the spaced-review queue (`vocabulary_review_state`) via `VocabularyReviewService.enrollLesson` — first due at the start of the next day, not yet recalled; items already in review keep their schedule, so replaying a lesson never resets one. A learner can also add any word by rating it on its word/phrase page (`VocabularyDetailView`); the Review tab's Start review opens `ReviewSessionScreen`, which snapshots everything due when it opens and saves each Again/Good/Easy rating through `VocabularyReviewService` (the same simplified SM-2 `SpacedReviewScheduler` the word pages use) as it goes, so closing early keeps what was rated. This is memory scheduling only — it never writes mastery evidence. The queue is one queue across levels, never narrowed to the level the learner is in. Weak Can-Do goals (`weakSpotsProvider`) are shown through `weakSpotsFor`, which groups them by the first non-mission lesson that teaches them, since the bundle has no learner-facing Can-Do text; it runs once per level with a unit in progress, against that level's own `masteryPolicy`, and each spot carries the level's CEFR code so its unit number reads unambiguously.

**Progress (learner):** learner completes an activity → written to local Drift immediately, insert-only (a replay appends a new attempt row rather than overwriting, so mastery history survives revisits) → a `MasteryAggregationService` recomputes cached per-unit/per-objective state from the evidence rows. For a signed-in learner the trigger-fed outbox then gets the new rows to their account a few seconds later (or when the device is next online) — see "Repositories and sync". A guest's progress never leaves the device.

**Free answers (ADR 0013):** a `speak` or `write` task graded by a `keywordChecklist` is graded in three steps. At submission the view runs the rubric (`evaluate()`), then — when the host allows signals (`gradingSignalsEnabled`: the lesson player and quick practice, never a `TestQuestionFrame` in the placement test or a capstone) and the task has model answers — asks `MeaningSignalService` how close the answer is to them. If the rubric is marked `onlineRefinement`, or an AI pack is installed, the answer is queued (`pending_online_refinements`, with its rubric score, meaning signal and `onlineAllowed`) and the panel says so; otherwise `combineSignals` produces the score at once and `passesWithSignals` the verdict, and `criteriaScoresJson` goes onto the attempt row. The drain resolves a queued row in order: the pack's judgement (through `judgementTaskFor`, which the provider resolves from the content index, since the drain itself never reads content) → the online grammar check, for a row allowed online → after enough failures or age, the signals already on the row. Every path ends in one `recordAttempt` with the signals recorded, and the panel or banner shows the pack's explanation, labelled generated, when there is one. The meaning service degrades to no signal on any failure; the pack to no judgement after three failures in a session.

**Test hosting:** all three tests open on `TestIntroView` and ask questions through `TestQuestionFrame`, which wraps the ordinary activity views in an `ActivityFrameScope` — the same frame as the lesson player. The placement test and final assessment set `testMode`, so the activity engine saves answers without marking them (no tile colours, no sound, a neutral "Answer saved" panel) and hides listening transcripts; scoring is unchanged and happens at the end. Each host counts an answer before saving it and awaits the save before moving on, since the feedback panel's Next appears as soon as Check is tapped.

**What the question frame shows:** `ActivityChrome` shows a question's `source` between the prompt and the answers (`ActivitySourceCard` — a `textChoice`'s `sourceText` or any activity's `sourceCard`), in test mode too, since the source is the question's input, not its answer. `SpeakActivityView` shows and reads aloud a speaking task's `partnerTurns`/`examinerTurns` before the learner answers (`ActivityPartnerTurnsCard`), replayable but never auto-playing in review, where several can be on screen at once. The lesson player's intro is the encounter conversation (`LessonConversationStep`, when the lesson has one) → the lesson's model text (`LessonReadingStep`, when the lesson has a `readingText`) → key phrases and grammar (`LessonKeyPhrasesStep`, shown only after a conversation or a text, and only when there are phrases or grammar to show) — with the key-phrases screen marking any earlier-level item "From A1" instead of NEW.

**Placement / Final Mission / Final Assessment (Phase 9):** the bundle has no dedicated placement-item pool at all (verified against the real data), so `PlacementItemSampler` draws receptive (listening/reading) items from each unit's own `practice`-mode activities, and its one productive (write/speak) supporting item from either `practice`- or `mastery`-mode content — real-content check showed every unit except `A1-U0` has zero `practice`-mode write/speak activities, so restricting to `practice` there would silently skip that step almost everywhere. What actually keeps a placement item out of real training/mastery evidence is the `sessionType='placement'` it's recorded under (`ActivityAttemptRepository.masteryEvidenceForObjective` filters to `sessionType='lesson'` only), never the source activity's own `mode`. The scan itself runs at two speeds (Design 4 of the A2 level-design spec). A **block pass** takes each level's units in blocks of three — four for A1, whose starter unit joins the opening block, so A1 is U0-U3, U4-U6, U7-U9, U10-U12 and A2 is U1-U3, … — and asks **one** item per unit, the block passing at the same 60% (`PlacementScoring.blockPassed`). Only a block that fails is opened up by a **drill-down**: its units in order, up to three fresh items each (`PlacementScoring.unitPassed`, which still refuses to fail a unit on fewer than two items), stopping at the first unit that fails — and *that* unit is the recommendation. A block whose units all pass on the second look simply carries on with the next block. Only drill-down results reach `PlacementClassifier`, which still stops at the **first** failing unit; a block that passed recommends nothing inside it. The effect is a test that reaches further and asks less: a complete beginner answers 7 items instead of 39, a learner who knows both levels 25. A unit's item sampling is seeded by its position in the plan and the drill-down excludes what the block pass already asked, so no item is ever repeated within an attempt. A single confidence self-report is collected afterward as supporting info only, never affecting the outcome. `PlacementTestScreen`'s item-sampling RNG seed is exposed via an overridable `placementSeedProvider` (the same pattern used for `TextToSpeechService`/`SpeechCapabilityService`), making the whole flow deterministically testable end-to-end despite depending on real random sampling in production — `test/features/placement_test/placement_test_screen_test.dart` drives one end-to-end pass per learner profile (beginner, gap inside A2, knows everything) and asserts how many questions each took. Final Mission and Final Assessment need no sampling (they read the bundle's own dedicated `finalMission`/`finalAssessment` objects directly); both are scored per skill/skill-group independently (`FinalMissionScoring`/`FinalAssessmentScoring`), never one blended average, and any item this app can't auto-grade (free-response writing/speaking with no `accepted` answer key) is reported `pendingReview` rather than guessed at — this app has no rubric evaluator yet, see [TECH_STACK.md](TECH_STACK.md).

## Cross-cutting concerns

- **Auth:** optional. Firebase Auth (email/password, Google, and Apple on iPhone — [ADR 0012](adr/0012-ios-release-sign-in-with-apple.md)) behind `AuthRepository`; signed-out learners use the device's guest learner. Firebase errors become `AuthFailure`s with bilingual messages (`auth_failure_message.dart`); sync errors become `SyncFailure`s that never reach the learner as errors. See [SECURITY.md](SECURITY.md) and [ADR 0010](adr/0010-optional-accounts-and-progress-sync.md).
- **Error handling:** typed exceptions thrown from the repository/content-parsing layers, caught and translated to user-facing messages at the UI layer — see [CONVENTIONS.md](CONVENTIONS.md). An unsupported/corrupted content bundle produces a typed `UnsupportedContentSchemaException`/`ParseError`, routed to a dedicated "unsupported content" screen, never a raw crash.
- **Logging / observability:** no analytics or crash-reporting SDK (see [ROADMAP.md](ROADMAP.md)); answers, personal text, and speech transcripts are never logged in release builds regardless. Sync and sign-in write developer logs through `dart:developer` (`mohingo.sync`, `mohingo.auth`): outcome, counts, conflicts and a 4-character account prefix — never emails, passwords, tokens or answers.
- **Config / secrets:** LLM API keys used for content generation live only in the separate dev-time authoring tool and are never bundled into the shipped app. The Firebase client configuration (`lib/firebase_options.dart`, `android/app/google-services.json`) is committed — it identifies the project and grants nothing by itself; see [FIREBASE_SETUP.md](FIREBASE_SETUP.md).

## Deployment topology

Mobile app distributed via the Apple App Store and Google Play. One **Firebase project** (Auth + Firestore; `firestore.rules` deployed with `firebase deploy --only firestore:rules`), whose **Hosting** serves the static support, privacy, terms and delete-account pages that `tool/legal/build_site.py` renders from `assets/legal/` ([ADR 0012](adr/0012-ios-release-sign-in-with-apple.md)) — no other hosted infrastructure, no custom server. See [FIREBASE_SETUP.md](FIREBASE_SETUP.md). The content-authoring tool runs locally on the author's machine, not deployed anywhere; its output is copied into the app repo as a versioned asset at build time.

## Start-up sequence (1.0.0)

1. Native launch screen (the app icon on the page colour, light or dark), then `/splash` while the base level's bundle loads.
2. `/welcome` — the first-run agreement — until `legal.acceptedAgreementVersion >= kAgreementVersion`. Its `/legal/*` documents stay reachable. Accepting redirects to `/home`.
3. Home, with the app guide (`AppGuideOverlay`) started once by `AppShellScaffold` while `appGuide.completedVersion < kAppGuideVersion`. Settings → App guide starts it again and switches to Home first.
4. The app. Sign-in is never part of this sequence: accounts stay optional, in Settings. See [ADR 0011](adr/0011-first-run-agreement-app-guide-and-account-deletion.md).
