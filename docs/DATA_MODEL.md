# Data Model

Two entirely separate stores, per [ARCHITECTURE.md](ARCHITECTURE.md), never merged:

- **Content** — one curriculum bundle per released level (`assets/content/en/A1/a1-course-bundle.json`, `assets/content/en/A2/a2-course-bundle.json`), each parsed into typed immutable models and indexed in memory, lazily, the first time something watches that level (the base level at startup). Read-only at runtime; the app never writes to it. Described in "Content entities" below.
- **Progress** — local Drift (SQLite) tables, the source of truth for everything the app renders about a learner's state. Described in "Progress entities (Drift)" below. Content-reference columns in these tables (`unitId`, `activityId`, `canDoId`, etc.) store the bundle's stable string IDs **directly** — Drift never mirrors or duplicates content.

There is no cloud store in v1 (no Firestore) — see [ADR 0004](adr/0004-local-only-v1-no-firebase-backend.md).

## Content entities (bundle-sourced, read-only)

Field lists below are the subset that matters for app logic, not an exhaustive schema — the bundle is the literal source of truth for exact shape.

### Course

One per level bundle; two exist (`a1`, `a2`). `id` (`"EN-A1-V2"`, `"EN-A2-V1"`), `title`/`titleAr`, `contentVersion`, `schemaVersion` (both bundles are `2.0.0`), `finalMissionId`, `finalAssessmentId`. A1 is `"A1-COMPLETE-2026.09.02"`; A2 still carries `"A2-IMPORT-2026.09.20"`, the string its import set — it was never bumped as the level was authored, so it names where the file came from, not what is in it. `course_enrolments.contentVersion` snapshots this string at enrolment, so an A2 enrolment records that value.

Sizes, for a sense of scale: A1 is 13 units / 89 lessons / 446 activities, with 85 grammar records, 354 lexical senses and 143 chunks; A2 is 12 units / 84 lessons / 432 activities, with 74 grammar records, 305 senses and 145 chunks. Each A2 unit is exactly 36 activities split 6 `encounter` / 12 `practice` / 18 `mastery`, and exactly 12 listening / 12 reading / 7 speaking / 3 writing / 2 mediation.

### Unit

`id` (e.g. `"A1-U1"`), `title`/`titleAr`, `levelRole`, `estimatedMinutes: [min,max]`, `countsTowardLevelMastery` (a level-neutral field: read from `countsTowardLevelMastery`, or from the older per-level names `countsTowardA1Mastery`/`countsTowardA2Mastery` a bundle may still use — A2's twelve units all carry `countsTowardA1Mastery: true`, inherited from the import, which is why the reader accepts any of the three names rather than trusting the key to name its own level), `lessons: [Lesson]`, `mastery: {requiredObjectives: [canDoId], requiredSkillGroups: [[skill]], minimumObjectiveScore, missionRequired, retry}`. **There is no Block entity** — A1 is 13 flat units (`A1-U0`…`A1-U12`), A2 is 12 (`A2-U1`…`A2-U12`, every one of them core, no starter); "Block" is superseded, see [GLOSSARY.md](GLOSSARY.md).

### Lesson

`id` (e.g. `"A1-U1-L1"`), `title`/`titleAr`, `lessonType`, `canDo: [canDoId]`, `grammar`/`lexicon`/`chunks: [registryId]` (the items this lesson introduces or draws on — for a level with a `prerequisiteLevelId`, an id here *may* belong to the earlier level, e.g. an A2 lesson listing `A1.G.BE.I_AM`, though no A2 lesson does: see "Content catalogue" below, [GLOSSARY.md](GLOSSARY.md)'s Earlier-level reference and [ADR 0006](adr/0006-multiple-levels.md)), optional `encounter: {dialogue: [{speaker, en, ar}], sceneAr?}` (58 of the 89 A1 lessons; 60 of A2's 84 — L1–L5 of every unit, each 5–8 lines and 2–3 named speakers with Arabic on every line; shown by the lesson player as its opening conversation, with the lesson's `chunks`/`grammar` as the key-phrases screen that follows — never recorded as attempts), optional `readingText: {title, text, textAr}` (`LessonReadingText` — a lesson's model text, e.g. a message or a profile, that its questions are about; 11 A1 lessons and every A2 unit's L6; shown by the lesson player between the conversation, when there is one, and the key-phrases screen), `activities: [Activity]`.

A2 lists 35–43 words and phrases per unit (462 listings across the level, against 305 lexical senses and 145 chunks in its registries, since a unit may recycle another's), and every listed item appears in that lesson's own conversation, text or activities — a content gate, not a convention (see [TESTING.md](TESTING.md)).

### Activity

Discriminated by `type` — one of `audioChoice`, `textChoice`, `match`, `order`, `gap`, `form`, `speak`, `write`, `dialogue` (the last declared in `domain.ACTIVITY_TYPES` but with no authored instances yet in the current bundle). Common fields: `id`, `mode` (`encounter`/`practice`/`mastery`), `skill`, `canDo: [canDoId]`, `prompt`/`promptAr`, optional `sourceCard` (string — the text a question is about or a mediation task's notice, shown with the question via `ActivitySourceCard`; a `textChoice` falls back to its own `sourceText` when `sourceCard` is absent). Type-specific fields (e.g. `options`/`answer` for choice types, `pairs` for `match`, `accepted`/`fallbackSkill`/optional `partnerTurns: [string]` for `speak` (the other person's lines, read aloud before the learner answers via `ActivityPartnerTurnsCard`; A1's older `examinerTurns` field is read the same way), `evaluation`/`wordGuide` for `write`; `evaluation` is a structured `{type, ...}` object — one of `nonEmpty`, `numericRange`, `letterSequence`, `keywordChecklist` — parsed by `EvaluationSpec.fromJson` in `lib/content/models/evaluation_spec.dart`, or `null` for content not yet migrated off the legacy opaque rubric-name string **and** for a recognized `type` whose required fields are missing or wrong-typed — an authoring error degrades to one un-auto-graded activity, never a throw that `CourseBundleParser` would turn into a whole-bundle `ContentParseException`; see docs/superpowers/specs/2026-09-07-offline-answer-evaluation-design.md) vary per type — see the content-model layer for the exact typed shape per type.

That silent degradation is why A2's gates check the *parsed* spec rather than the JSON: the imported bundle's 120 productive activities all carried a legacy rubric-name array, which parses to `null`, so every speaking, writing and mediation task in the level looked graded in the file and reached the app ungraded. All 144 of A2's speak/write activities now carry a `keywordChecklist`, all 36 of its `spokenInteraction` tasks carry `partnerTurns`, and all 24 of its mediation tasks carry a `sourceCard` — the material the task asks the learner to relay, which none of them supplied at import.

### Grammar / Lexicon / Chunk (registries)

- **Grammar**: `id` (e.g. `"A1.G.BE.I_AM"`), `form`, `shortForm`, `meaningAr`, `introducedIn` (lessonId), `examples: [{en, ar}]`.
- **Lexicon**: `id`, `headword`, `partOfSpeech`, `arabic`, `receptive`/`productive` (bool), `meaning`, `examples: [string | {en, ar}]` (A1's examples are plain English strings; a level may instead give bilingual `{en, ar}` example objects — both shapes parse), `introducedIn`, `recycledIn: [lessonId]`. Two records may share a `headword` while being distinct senses (e.g. `A1.LEX.PICTURE.N01` vs `N02`) — always keyed and treated by `id`, never by spelling.
- **Chunk**: `id`, `text`, `arabic`, `introducedIn`, `productive`, `recycledIn`.

### Media specification

Keyed by a string id (either a standalone scene id or a `ttsSource`'s own key). Two kinds:
- **`ttsSource`**: `{locale, voiceProfile, transcript, activityId}` — read aloud by on-device TTS at runtime; no pre-recorded audio file exists anywhere in the bundle.
- **Structured scene types** (`peopleCard`, `personCard`, `peopleMap`, `homePlan`, `objectScene`, `distanceScene`, `apartmentPlan`): data describing a diagram to render (e.g. `{people: [{id, role}], links: [[id, id, relation]]}`), not artwork — rendered by app-owned diagram widgets, see [ARCHITECTURE.md](ARCHITECTURE.md).

### Final Mission / Final Assessment

One of each per level. A1's are reachable from the Tests tab; A2's (`A2-FINAL-MISSION` "Host a Visitor", `A2-FINAL-ASSESSMENT`) exist in the bundle and are gated by `test/content/a2_capstones_test.dart`, but nothing in the UI opens them yet — the Tests tab reads `'a1'` directly (step 2b, see [ROADMAP.md](ROADMAP.md)).

- **`FinalMission`**: `id` (`"A1-FINAL-MISSION"`), `scenario`, `canDo: [canDoId]` (EXIT_* ids), `stages: [{id, activityIds}]` (6 stages, 12 activities in both levels), `activities: [Activity]`, `scoring: {completionRequired, requiredSkillGroups, criteria, minimumCriterionScore, speechAccuracyWeight, noSingleAverageCompensation}`.
- **`FinalAssessment`**: `id` (`"A1-FINAL-ASSESSMENT"`), `sourcePolicy` (secure/unseen inputs), `sections: {listening, reading, writing, speaking, mediation}` (each with its own `activities`; A2's is 18/18/2/4/2 = 44 items), `scoring` per-section (e.g. `speaking: {criteria, minimumTaskCriterionAverage, minimumCompletedTasks, accuracyWeight}`, plus `decisionRule: {noSingleOverallAverage, required: [skill], capstoneMissionRequired}` and `accessibility: {microphoneFallback: "writing", fallbackDoesNotCreateSpeakingEvidence: true}`).

Every pass mark in both levels' capstones is **0.6** — the assessment's per-skill minimums and the mission's `minimumCriterionScore`. A2's import shipped 0.75 and it was lowered deliberately: both exits are marked by the same keyword evaluator, so a stricter bar on A2 would make "finished A1" and "finished A2" mean different things. Unit mastery is unaffected and stays at 0.75 (`MASTERY_POLICY.minimumObjectiveScore`). `capstonePassMark` in `test/content/a2_capstone_checks.dart` is what stops it drifting back.

### Domain definitions

`SKILLS` (6 values: `listening`, `reading`, `writing`, `spokenInteraction`, `spokenProduction`, `mediation`), `MODES` (`encounter`/`practice`/`mastery`), `ACTIVITY_TYPES` (9 values, see Activity above), `CAN_DO` (a flat map per level — 103 ids in A1, 91 in A2), `MASTERY_POLICY` (identical in both bundles) (`minimumObjectiveScore: 0.75`, `minimumEvidencePerRequiredObjective: 2`, `requireProductiveEvidenceWhereDeclared: true`, `practiceCountsAsMastery: false`, `allowSpeechFallbackToWriting: true`, `speechCriteria`, `speechAccuracyWeight: 0.2`).

### Content catalogue

Not part of the bundle — a small, app-owned static table mapping `levelId` (`a1`..`c2`) to `LevelAvailability` (`available`/`preview`/`comingSoon`), the asset path to load when one exists, and, per level, the level it builds on (`prerequisiteLevelId`: A2 → A1, null for A1). `preview` sits between the other two: the level's bundle loads and a learner can browse its units, but its lessons stay closed until release. Today `a1` and `a2` are both `available` (both have a `bundleAssetPath`) and `b1`-`c2` are `comingSoon` (no bundle at all); no level is in `preview` since A2 was released on 2026-09-21, and that state is how the next level will ship while it is being written. A development build can promote a `preview` level to `available` with `--dart-define=MOHINGO_PREVIEW_LEVELS=<levelId>` (`applyPreviewOverrides`). See [ADR 0006](adr/0006-multiple-levels.md), [GLOSSARY.md](GLOSSARY.md)'s Earlier-level reference and Level lock, and [ARCHITECTURE.md](ARCHITECTURE.md)'s "Current level and level lock".

## Progress entities (Drift, local, source of truth for learner state)

Every table has a local autoincrement `id` (SQLite-internal only, never exposed outside the DB layer) **and** a separate `uuid TEXT UNIQUE` column (app-level stable identity, for a future sync layer — see [ADR 0004](adr/0004-local-only-v1-no-firebase-backend.md)). These are distinct concerns and are never conflated.

### learners

| Field | Type | Constraints | Notes |
|---|---|---|---|
| id | int | PK, autoincrement | local row identity only |
| uuid | string | UNIQUE | replaces the old Firebase-Auth-UID identity — generated locally on first launch |
| nativeLanguage | enum | fixed to `ar` for MVP | not user-editable in MVP |
| targetLanguage | enum | fixed to `en` for MVP | not user-editable in MVP |
| createdAt | timestamp | | |
| isActive | bool | | v1 never exposes profile switching; kept as a real table, not a single-row blob, so a future multi-profile/sync-merge scenario needs no schema change |
| name | string | nullable | the learner's own name, set via Settings; used only by the `letterSequence`/`profileName` evaluation reference (see the Activity section above), never required for anything else. |

### course_enrolments

`id`, `uuid`, `learnerId` FK, `courseId` (bundle `course.id`, e.g. `"EN-A1-V2"`), `contentVersion` (bundle `contentVersion` at enrolment time — anchors "which content version was this progress recorded against"), `enrolledAt`, `status`, `levelId` (nullable — the catalogue key this enrolment is for, e.g. `"a1"`/`"a2"`; null on a row written before schema v5, read as the base level and backfilled to it the next time `ensureEnrolled` sees it), `lastSelectedAt` (nullable — when the learner last made this level the one they're working in; across a learner's enrolments, the most recent value is their **current level**, `kBaseLevelId` when none is set — see [GLOSSARY.md](GLOSSARY.md)'s Current level), `unlockedAt` (nullable — set only when the learner chose to open this level before finishing the one it builds on, via the lock sheet's "Open anyway"; null otherwise, including for a level that's open because its prerequisite is complete, which needs no unlock row). One row per learner per level they're enrolled in, created lazily: `MohingoApp` enrols the learner in `currentLevelIdProvider`'s level as soon as the profile and that level's content are ready, and `LevelSelectionController.select`/`.unlock` enrol explicitly on switch/unlock — never for a level the learner is only browsing (see [ARCHITECTURE.md](ARCHITECTURE.md)'s "Current level and level lock").

### unit_progress

`id`, `uuid`, `learnerId`, `unitId` (string, bundle id), `state` (`notStarted`/`inProgress`/`needsReview`/`mastered`), `lastActivityAt`, `masteredAt`, `isContentStale`, `updatedAt`. **A read-model** — recomputed by a `MasteryAggregationService` from `activity_attempts`/`activity_attempt_can_dos`, cached here for fast Home/Learn queries; never hand-edited directly by a UI action.

### lesson_progress

`id`, `uuid`, `learnerId`, `lessonId`, `unitId` (denormalized), `state`, `lastActivityId` (resume pointer, written after every meaningful event — not just at lesson end), `lastPositionUpdatedAt`, `updatedAt`.

### activity_attempts

`id`, `uuid`, `learnerId`, `activityId` (string, bundle id — or the mission/assessment item's own id namespace), `lessonId` (nullable — null for placement/mission/assessment items), `sessionType` (`lesson`/`practiceReview`/`placement`/`finalMission`/`finalAssessment`), `sessionId` (nullable, links to the relevant attempt table's `uuid`), `mode` (`encounter`/`practice`/`mastery`, copied at record time so history stays self-describing even if content changes later), `evidenceSkill`, `rawAnswer` (JSON), `isCorrect`, `score`, `criteriaScores` (JSON), `wasFallback`, `attemptedAt`, `updatedAt`. **Insert-only, never updated** — a replayed activity appends a new row rather than overwriting, so a learner revisiting a completed unit never corrupts prior mastery history.

`evidenceSkill` normally equals the activity's declared `skill`; when a `speak` activity is answered via its bundle-declared `fallbackSkill: "writing"`, `wasFallback=true` and `evidenceSkill='writing'` are written at record time — this is the concrete mechanism implementing the bundle's own `fallbackDoesNotCreateSpeakingEvidence` rule (present on `finalAssessment.scoring.accessibility` and mirrored for unit/mission `speak` activities).

### activity_attempt_can_dos

`id`, `attemptId` FK, `canDoId` (string). Normalizes an activity's `canDo: [id]` array into one row per (attempt × canDo) pair, so mastery aggregation is a single indexed SQL `GROUP BY canDoId, evidenceSkill` join rather than per-row JSON scanning in Dart.

### pending_online_refinements

`id`, `uuid`, `learnerId`, `activityId`, `lessonId`, `unitId` (denormalized so a resolved item can refresh that unit's cached mastery state without a content lookup), `canDoIds` (JSON-encoded `[canDoId]`), `rawAnswer` (JSON-encoded, exactly like `activity_attempts.rawAnswer` — decoded to plain text only for the grammar check itself, never for storage), `evidenceSkill`, `wasFallback`, `mode`, `localScore` (the offline `keywordChecklist` content score, computed once at submission), `submittedAt`, `attemptCount`, `lastAttemptAt`. `evidenceSkill` and `wasFallback` are carried through the queue verbatim and written unchanged onto the resulting `activity_attempts` row, so the `wasFallback=true` + fallback-skill pairing documented above survives deferred grading — a typed answer to a `speak` activity never becomes speaking evidence just because it was graded later. Unlike most other progress tables (which are updated in place) or `activity_attempts` (which is strictly insert-only), rows here are deleted outright once resolved — the only table in this app where a row's whole lifecycle ends in a real DELETE, not an update or a permanent insert. One row per submitted open-ended answer awaiting a free online grammar-quality pass; removed the moment it resolves (online, or via the bounded local-only fallback) into exactly one ordinary `activity_attempts` row, which also triggers a `MasteryAggregationService.refreshUnitProgress` for `unitId`. See docs/superpowers/specs/2026-09-07-offline-answer-evaluation-design.md's Tier 2 and [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md).

### placement_attempts / final_mission_attempts / final_assessment_attempts

Each holds one row per attempt at that assessment (`id`, `uuid`, `learnerId`, `startedAt`, `completedAt`, plus an outcome summary specific to that assessment type — e.g. `placement_attempts.outcome` is one of the four actionable placement outcomes, never a level the app has no content for). `placement_attempts.outcome` stores a **string**, not an enum name, for the one outcome that names a level: a mastered level is written as `"<levelId>Mastered"` (`a1Mastered`, `a2Mastered`), so a result recorded when A1 was the only released level keeps saying A1 after A2 ships instead of being re-read as a claim about it — `masteredLevelIdOfStoredOutcome` reads both. The other three outcomes store their enum name unchanged (`startWithEssentials`, `startA1FromU1`, `startFromRecommendedUnit`) and carry their level in `recommendedUnitId`, whose prefix names it. `placement_attempts.stageReached` counts the **units the scan reached** (the test walks blocks of units, not numbered stages — see [ARCHITECTURE.md](ARCHITECTURE.md)); it is written, never read. Per-item results for all three live in `activity_attempts`, filtered by `sessionType`. Kept as separate attempt tables (not folded into `course_enrolments`) so retakes are isolated and item-answer state never leaks into ordinary lesson Review — see [ARCHITECTURE.md](ARCHITECTURE.md).

### vocabulary_review_state

`id`, `uuid`, `learnerId`, `lexiconId` (nullable) or `chunkId` (nullable, exactly one set), `isFavorite`, `confidenceMarker`, `easeFactor`, `intervalDays`, `repetitions`, `dueAt`, `lastReviewedAt`, `updatedAt`. Created lazily — when the lesson that teaches the item is finished (`enrollVocabulary`: `dueAt` = start of the next day, `repetitions` 0; an existing scheduled row is left untouched, a favourite-only row just gets its `dueAt`), or on first favourite/rating — never pre-populated for all ~500 lexicon+chunk records at enrolment. `easeFactor`/`intervalDays`/`repetitions`/`dueAt` are computed by a genuine SM-2 (SuperMemo-2) scheduler (`SpacedReviewScheduler`) driven by a simplified 3-button Again/Good/Easy confidence input — see its doc comment for the exact formula. This schedule is vocabulary-memory only; it never grants or affects Can-Do mastery, which lives entirely in `activity_attempts`/`unit_progress` instead.

### grammar_review_state

`id`, `uuid`, `learnerId`, `grammarId`, `isFavorite`, `markedReviewedAt`, `updatedAt`. `markedReviewedAt` is a UI-only checkbox — it never flips any Can-Do objective's mastered state.

### daily_task_events

`id`, `uuid`, `learnerId`, `taskType` (`lesson`/`vocabularyReview`/`speaking`), `occurredAt`. **Insert-only**, like `activity_attempts` — never updated or deduplicated at write time, since Home only ever reads *counts per calendar day* (`DailyTaskEventRepository.countsForToday`, same local-day convention as `activity_attempts.currentStreakDays` — no UTC normalization). Backs Home's "Tasks today" row (Finish a lesson / Review 5 words / Speak once). Each `taskType` is written from a single existing choke point, not a new call site per feature: `speaking` from `DriftActivityAttemptRepository.recordAttempt` (only when `evidenceSkill` is `spokenProduction`/`spokenInteraction` — a `speak` activity graded via its typed fallback, `evidenceSkill='writing'`, never writes one, since a fallback answer didn't actually speak), `vocabularyReview` from `VocabularyReviewService.recordReview` (every graded word, any confidence quality), and `lesson` from `LessonPlayerScreen`'s final-activity handler (the one place a lesson actually finishing is known — there is no dedicated "lesson completed" event anywhere else in the schema, unlike `unit_progress`/`lesson_progress` which only track fuzzier multi-lesson/multi-day state).

### content_versions

`id`, `contentVersion`, `schemaVersion`, `courseId`, `installedAt`, `unitIdsJson`, `lessonIdsJson`, `activityIdsJson`, `canDoIdsJson`. Append-only log of every bundle version loaded on-device; the id-set snapshots (not the full bundle) are what makes detecting removed ids possible when content updates later, without re-parsing history.

### Device/UI preferences — deliberately not in this list

Theme mode, colour theme, interface language, text scale, TTS voice/rate/pitch, and the "seen onboarding" flag live in `shared_preferences`, not Drift — see [TECH_STACK.md](TECH_STACK.md). Keeping them out of Drift means "reset progress" in Settings can never accidentally also reset a learner's language/theme.

## Relationships

One `Course` (bundle) has many `Unit`s; one `Unit` has many `Lesson`s; one `Lesson` has many `Activity`s. `Lesson`s and `Activity`s reference `Grammar`/`Lexicon`/`Chunk` registry items and `CAN_DO` objective ids by string id — never by duplicating the referenced record.

One `learners` row has many `course_enrolments`, `unit_progress`, `lesson_progress`, `activity_attempts` (across all `sessionType`s), `placement_attempts`, `final_mission_attempts`, `final_assessment_attempts`, `vocabulary_review_state`, and `grammar_review_state` rows. One `activity_attempts` row has one-to-many `activity_attempt_can_dos` rows (mirroring the source activity's `canDo` array at attempt time).

## Key constraints & invariants

- **Content and progress never mix.** No Drift table stores curriculum text/prompts/options; no content model stores a learner's answers. Content-reference columns store bundle string ids verbatim.
- **Mastery is per-`(canDoId, evidenceSkill, mode)`, not a single score.** A Can-Do objective is "mastered" per `MASTERY_POLICY`: enough `mode='mastery'` evidence rows (`minimumEvidencePerRequiredObjective`), each meeting `minimumObjectiveScore`, with productive evidence present where the unit's `requiredSkillGroups` declare it required. `practiceCountsAsMastery` is always `false` — `mode='practice'` rows are never counted. A learner who can recognise language but not produce it must not show as fully mastered — see [PRODUCT.md](PRODUCT.md) and the curriculum's own non-negotiable rule (`docs/a1-modular-course/README_AR.md`).
- **Attempts are insert-only.** Revisiting a completed unit/activity appends new `activity_attempts` rows; nothing is ever overwritten or deleted, so mastery history is always reconstructable. The one deliberate exception is a learner explicitly choosing "Reset progress" in Settings (`AppDatabase.resetProgressForLearner`) — a confirmed, destructive, learner-initiated action (see [UX_PRINCIPLES.md](UX_PRINCIPLES.md)'s confirmation-copy rule) that deletes every progress/attempt/review row for that learner across every table listed here, while leaving the `learners` row itself (and its uuid) untouched — it resets progress, not identity.
- **A speaking fallback never creates speaking evidence.** Encoded at write time via `evidenceSkill`/`wasFallback`, not derived at read time — see `activity_attempts` above.
- **Assessment inputs stay isolated from training.** `placement`/`finalMission`/`finalAssessment` attempts are never surfaced through ordinary Review screens, which query `activity_attempts` filtered to `sessionType='lesson'` only.
- **A Unit's progression is a recommendation, not a hard lock.** `unit_progress.state` drives the "Continue learning" suggestion and unit badges; it never blocks navigation to another unit — see [PRODUCT.md](PRODUCT.md) flow 5 and [ARCHITECTURE.md](ARCHITECTURE.md)'s navigation guards.
- `nativeLanguage`/`targetLanguage` are fixed (`ar`/`en`) for the MVP; the schema allows other values so this isn't a hard rewrite later, but no UI exists to change them yet.
- **No PII beyond what's listed in [SECURITY.md](SECURITY.md)** is ever written to `activity_attempts.rawAnswer`. For a speaking activity that means the **recognised text is stored** (JSON-encoded, like any other answer) while the audio never is: the Learn tab's read-only answer review reads that row back to show a learner what they said (`SpeakActivityView`'s `reviewAttempt`), so discarding it would empty the feature. This corrects a claim this doc and [SECURITY.md](SECURITY.md) both carried from before the 2026-09-09 answer-review feature — that a transcript is "discarded after scoring". It isn't; it is progress data, cleared with the rest by "Reset progress".
