> **What this file is:** The auth model, how secrets are handled, and the hard limits nothing should cross (e.g. "never log PII"). Security rules are exactly the kind of thing that must never be re-derived per session — they must be inherited.

# Security

## Auth model (v1)

- **No accounts, no sign-in, no Firebase Auth in v1.** A single local `Learner` profile is created automatically on first launch, identified by a locally-generated stable UUID (see [DATA_MODEL.md](DATA_MODEL.md)) — there is nothing to authenticate against, since there is no backend at all.
- Roles/permissions: single implicit role — `Learner`. No in-app admin/author role; content authoring happens entirely outside the app via the separate dev-time curriculum tool (`reference/a1-modular-course/`), which never runs on a learner's device (see [ARCHITECTURE.md](ARCHITECTURE.md)).
- **Deferred, post-v1:** Firebase Auth (email/password at minimum; Sign in with Apple required if any other third-party sign-in is offered, per App Store rules), once account-based sync is built — the original direction in [ADR 0001](adr/0001-offline-first-firebase-only-backend.md), now scoped to that later phase per [ADR 0004](adr/0004-local-only-v1-no-firebase-backend.md).

## Secrets handling

- Where secrets live: LLM API keys used for content generation live only in the separate dev-time authoring tool's local environment (e.g. `.env`, gitignored) — never bundled into the shipped app, never committed. Unchanged by the local-only decision — this rule was never about Firebase.
- **No Firebase client config is bundled in v1** — there is no Firebase SDK usage at all, so `google-services.json`/`GoogleService-Info.plist` don't apply until the deferred post-v1 sync phase.
- The speech-audio tool (`tool/audio/`, [ADR 0008](adr/0008-bundled-pre-generated-speech-audio.md)) holds no credential today: Kokoro runs on the authoring machine. If a cloud voice (e.g. Google Chirp 3 HD) is ever added, its key follows the LLM key's rule — the tool's local environment only, never the app, which is why the app plays clips rather than calling any engine.
- Rule: never commit secrets, never ship secrets to the client (standing rule).

## Data handling

- PII fields (v1): `Learner.nativeLanguage`/`targetLanguage` (personal but not sensitive), Attempt history (learning progress) — see [DATA_MODEL.md](DATA_MODEL.md). No auth email or auth tokens exist in v1, since there are no accounts.
- What must never be logged: any learner-entered answer text, any speech transcript, the local learner UUID. Speaking activities are transcribed on-device only (see [TECH_STACK.md](TECH_STACK.md)) — raw audio is never uploaded (there is no server to upload to in v1), never stored at rest, and never logged. The **recognised text**, however, *is* stored, in `activity_attempts.rawAnswer` like any other answer: the Learn tab's read-only answer review (2026-09-09) reads it back to show a learner what they said, so it is progress data with a lifetime, not a scratch value. This doc said the opposite until 2026-09-21 — "discarded after scoring" — which stopped being true when that feature landed and nobody corrected the rule. It is deleted with the rest of a learner's progress by Settings' "Reset progress"; see [DATA_MODEL.md](DATA_MODEL.md).
- Encryption at rest / in transit: no data leaves the device in v1, **with one narrow, bounded exception**: an open-ended writing/speaking answer (a rubric marked `onlineRefinement`, see [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md)), when the device is online, may be sent over HTTPS to the free public LanguageTool API for a grammar-quality check — never blocking, never required (a bounded local-only fallback resolves it either way). The learner sees a message indicating the answer will be checked further when they are online, but the message does not disclose the specific service or that the answer leaves the device; they are informed only that additional grading occurs with a local-only fallback available. See [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md).
  - **How wide that exception is, counted rather than estimated (2026-09-21).** **59 rubrics across both shipped levels, every one of them a `write` task, none of them in a capstone** — 23 in A1's units, 36 in A2's. Both capstones of both levels grade offline-only. Nothing a learner says ever takes this path: the answer that leaves the device is always text they typed.
  - **How that was nearly not true, and what now holds it.** A2's authoring applied one rubric template to speaking and writing alike, marking 114 `speak` tasks in the units and 6 in the Final Mission. `SpeakActivityView` honours `onlineRefinement` on whatever activity carries it, so each of those would have queued the learner's **recognised speech text** (`pending_online_refinements.rawAnswer`) for the public LanguageTool API — a verbatim transcript leaving the device, which ADR 0005 excludes in as many words. Commit `1893e23` unmarked all 120 before release. Nobody had decided to widen it and no gate had noticed, because the boundary was written only in an ADR; `test/content/online_refinement_boundary_test.dart` now fails on any `speak` rubric in any shipped bundle that carries the mark. Widening this exception to speech is a decision that needs its own ADR, not an authoring default.

  The local Drift database is not encrypted by default for v1 — acceptable given the limited PII involved (no payment data, no accounts); revisit if that changes.

## Hard limits

- No client-side secret keys — neither the LLM API key nor any speech-engine key is ever bundled into the shipped app; speech ships as audio files.
- **No network permission or background network call is required for any learning feature in v1** — still true after [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md): online grammar refinement for open-ended answers is a bounded quality upgrade with a working offline fallback, never a requirement. Note: Android requires declaring the `INTERNET` permission in its manifest (a build-time declaration, not a runtime prompt); this is accounted for in `android/app/src/main/AndroidManifest.xml`.
- Microphone permission is requested only when a learner deliberately starts a speaking task, never on activity mount or app launch — see [ARCHITECTURE.md](ARCHITECTURE.md)'s speech feature and [TECH_STACK.md](TECH_STACK.md).
- All external input (activity answers, placement-test responses) validated before being written to Drift — never trust client-submitted data as pre-validated when it affects mastery evidence.
- **Deferred, post-v1:** Firestore/Storage Security Rules enforcing per-learner data isolation, once accounts and sync exist (see [API_CONTRACT.md](API_CONTRACT.md), currently N/A for v1).

## Dependency / vulnerability policy

Solo project — lightweight policy: periodically run `flutter pub outdated`, review changelogs before upgrading — with particular attention to `drift`/`drift_flutter` (local data access), `speech_to_text`/`flutter_tts`/`permission_handler` (microphone access, a sensitive OS permission) — and prioritize security patches over feature-driven upgrades. Revisit this list to include Firebase SDKs once the deferred post-v1 sync phase adds them.
