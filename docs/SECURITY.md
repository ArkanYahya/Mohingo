# Security

## Auth model

- **Accounts are optional** ([ADR 0010](adr/0010-optional-accounts-and-progress-sync.md)). Without one, the device's guest learner (a local UUID) holds the progress and nothing is uploaded. With one, Firebase Authentication identifies the learner by their Firebase UID.
- Providers: **Email/Password** (Firebase enforces its minimum length; the app asks for 6+ characters and a confirmation) and **Google** (`google_sign_in` → Firebase credential). Password reset goes through Firebase's own email; the app never says whether an address has an account (the reset confirmation reads the same either way; email-enumeration protection stays on in the console).
- Sessions: Firebase keeps the sign-in on the device between launches and refreshes its tokens itself; the app never reads, stores or logs a token. An expired or revoked session surfaces as `SyncFailure.signedOut` ("sign in again"); local learning is unaffected.
- **Account isolation on the device:** every account gets its own local learner row (`learners.firebase_uid`); signing out switches to the guest, signing in as someone else never shows the previous account's progress, and the sync engine refuses to upload a learner that isn't bound to the signed-in account. Guest progress becomes an account's only when the learner chooses "Add to my account".
- Roles/permissions: single implicit role — `Learner`. No in-app admin/author role; content authoring happens entirely outside the app via the separate dev-time curriculum tool (`reference/a1-modular-course/`), which never runs on a learner's device (see [ARCHITECTURE.md](ARCHITECTURE.md)).
- **Store obligations, not yet met** (see [ROADMAP.md](ROADMAP.md)): in-app account deletion (Google Play policy for apps that create accounts) before a Play release; Sign in with Apple before Google sign-in ships on iOS (App Store guideline 4.8).

## Secrets handling

- Where secrets live: LLM API keys used for content generation live only in the separate dev-time authoring tool's local environment (e.g. `.env`, gitignored) — never bundled into the shipped app, never committed. Unchanged by the local-only decision — this rule was never about Firebase.
- **The Firebase client config is committed, and is not a secret**: `lib/firebase_options.dart`, `android/app/google-services.json`, `.firebaserc`. They identify the project; access is decided by sign-in and Security Rules. Restrict the Android API key to the app's package and SHA-1s in the Cloud console ([FIREBASE_SETUP.md](FIREBASE_SETUP.md)). Never commit a service-account key or any admin credential — nothing in this app needs one.
- The speech-audio tool (`tool/audio/`, [ADR 0008](adr/0008-bundled-pre-generated-speech-audio.md)) holds no credential today: Kokoro runs on the authoring machine. If a cloud voice (e.g. Google Chirp 3 HD) is ever added, its key follows the LLM key's rule — the tool's local environment only, never the app, which is why the app plays clips rather than calling any engine.
- Rule: never commit secrets, never ship secrets to the client (standing rule).

## Data handling

- PII fields: `Learner.nativeLanguage`/`targetLanguage` (personal but not sensitive), the optional display name, attempt history (learning progress, including typed answers and recognised speech text) — see [DATA_MODEL.md](DATA_MODEL.md). For a signed-in learner, the account's email lives in Firebase Auth only; it is never written to Firestore or the local database.
- **What leaves the device for a signed-in learner:** their progress records, exactly as listed in [API_CONTRACT.md](API_CONTRACT.md) — including answer text and recognised speech text, since those are progress (answer review reads them). Never raw audio. A guest's progress never leaves the device.
- What must never be logged: any learner-entered answer text, any speech transcript, the local learner UUID, a password, an auth token, an email address. Sync logs (`mohingo.sync`, via `dart:developer`, not printed in release) carry only outcomes, counts, collection names and the first 4 characters of the account id. Speaking activities are transcribed on-device only (see [TECH_STACK.md](TECH_STACK.md)) — raw audio is never uploaded (there is no server to upload to in v1), never stored at rest, and never logged. The **recognised text**, however, *is* stored, in `activity_attempts.rawAnswer` like any other answer: the Learn tab's read-only answer review (2026-09-09) reads it back to show a learner what they said, so it is progress data with a lifetime, not a scratch value. This doc said the opposite until 2026-09-21 — "discarded after scoring" — which stopped being true when that feature landed and nobody corrected the rule. It is deleted with the rest of a learner's progress by Settings' "Reset progress"; see [DATA_MODEL.md](DATA_MODEL.md).
- Encryption at rest / in transit: no data leaves the device in v1, **with one narrow, bounded exception**: an open-ended writing/speaking answer (a rubric marked `onlineRefinement`, see [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md)), when the device is online, may be sent over HTTPS to the free public LanguageTool API for a grammar-quality check — never blocking, never required (a bounded local-only fallback resolves it either way). The learner sees a message indicating the answer will be checked further when they are online, but the message does not disclose the specific service or that the answer leaves the device; they are informed only that additional grading occurs with a local-only fallback available. See [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md).
  - **How wide that exception is, counted rather than estimated (2026-09-21).** **59 rubrics across both shipped levels, every one of them a `write` task, none of them in a capstone** — 23 in A1's units, 36 in A2's. Both capstones of both levels grade offline-only. Nothing a learner says ever takes this path: the answer that leaves the device is always text they typed.
  - **How that was nearly not true, and what now holds it.** A2's authoring applied one rubric template to speaking and writing alike, marking 114 `speak` tasks in the units and 6 in the Final Mission. `SpeakActivityView` honours `onlineRefinement` on whatever activity carries it, so each of those would have queued the learner's **recognised speech text** (`pending_online_refinements.rawAnswer`) for the public LanguageTool API — a verbatim transcript leaving the device, which ADR 0005 excludes in as many words. Commit `1893e23` unmarked all 120 before release. Nobody had decided to widen it and no gate had noticed, because the boundary was written only in an ADR; `test/content/online_refinement_boundary_test.dart` now fails on any `speak` rubric in any shipped bundle that carries the mark. Widening this exception to speech is a decision that needs its own ADR, not an authoring default.

  In transit, sync uses Firestore's TLS. At rest in the cloud, Firestore encrypts by default. The local Drift database is not encrypted — acceptable given the limited PII involved (no payment data, no passwords or tokens in it); a signed-out account's progress stays on the device until that account signs in again, which is a documented trade-off (a shared phone keeps it; "Reset progress" while signed in removes it everywhere).

## Hard limits

- No client-side secret keys — neither the LLM API key nor any speech-engine key is ever bundled into the shipped app; speech ships as audio files.
- **No network permission or background network call is required for any learning feature in v1** — still true after [ADR 0005](adr/0005-narrow-network-exception-for-open-ended-grading.md): online grammar refinement for open-ended answers is a bounded quality upgrade with a working offline fallback, never a requirement. Note: Android requires declaring the `INTERNET` permission in its manifest (a build-time declaration, not a runtime prompt); this is accounted for in `android/app/src/main/AndroidManifest.xml`.
- Microphone permission is requested only when a learner deliberately starts a speaking task, never on activity mount or app launch — see [ARCHITECTURE.md](ARCHITECTURE.md)'s speech feature and [TECH_STACK.md](TECH_STACK.md).
- All external input (activity answers, placement-test responses) validated before being written to Drift — never trust client-submitted data as pre-validated when it affects mastery evidence.
- **Firestore is never in test mode.** `firestore.rules` admits only the signed-in owner to `users/{uid}/**`, validates every document's exact shape, keeps answers immutable, forbids lowering the reset epoch, and denies everything else. Any change to the synced schema changes the rules and `tool/firestore_rules_test/` in the same commit. Storage is unused and has no rules to keep open.
- Sign-in and sync are never required for a learning feature: a failure is shown as a status on the Settings account row, never as a blocking error.

## Dependency / vulnerability policy

Solo project — lightweight policy: periodically run `flutter pub outdated`, review changelogs before upgrading — with particular attention to `drift`/`drift_flutter` (local data access), `speech_to_text`/`flutter_tts`/`permission_handler` (microphone access, a sensitive OS permission) — and prioritize security patches over feature-driven upgrades. The Firebase SDKs (`firebase_core`, `firebase_auth`, `cloud_firestore`, `google_sign_in`) are on that list too.
